# CLI 工具设计最佳实践

编写或评审 CLI 工具前，完整阅读 [reference/cli-tool-design-principles.md](reference/cli-tool-design-principles.md)。局部低风险修复至少阅读其中的「什么时候该参考这份原则」「总体设计纲领」和「开发新 CLI 时的检查清单」。

## 工作流程

1. 判断工具是否会修改文件、配置、权限、服务、远程主机或其他系统状态。
2. 编码前给出覆盖 4 层的最小设计计划：
    - 参数层：参数解析、参数校验、配置来源；
    - 检查层：权限、系统环境、依赖命令、目标路径、远程连通性；
    - 执行层：显式步骤、失败即停、可重复执行；
    - 反馈层：`stdout`、`stderr`、日志、错误摘要、退出码。
3. 只实现当前要求的能力，不为未来需求提前扩展。
4. 为关键路径和失败路径补充或更新测试。
5. 结束前按参考文档的检查清单自检。

## 硬性底线

- 先做前置检查，再做高风险动作。
- 关键步骤失败后默认停止。
- `main()` 或入口层返回明确退出码。
- 密码、令牌、私钥、连接串等敏感信息默认脱敏，不写入普通输出或日志。

## 实现偏好

- 分离参数解析、流程编排和核心业务逻辑。
- 让外部命令执行器、输入输出流、时间和权限检查等可注入，便于测试。
- 默认面向人类的输出保持克制；机器可读结果提供 `--json` 或等价选项。
- 对改变系统状态的操作，优先支持 `--dry-run`、备份、确认或显式 `--force-*`。
- 目标项目已有更具体规范时，先遵循项目规范，再用本 Skill 补充 CLI 设计检查。
