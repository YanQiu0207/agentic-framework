# 经验沉淀 (Self-Refinement)

## 核心定位

**从错误中构建反馈闭环**：机械可判定的违规优先转化为确定性检查，需要判断的经验沉淀到 Rules/Skills，降低同类错误重复发生的风险。

> 持久化规则不等于执行保证；能机器判定的约束，应通过实际接线的检查阻止复发。

---

## 触发模式

### 模式一：自动触发

**触发条件**：用户明确纠正 AI，且暴露出可复用、跨会话可能重复的错误模式。普通澄清、否定、语气不满、一次性偏好或任务改向不触发。

**行为**：
1. **先完成当前纠正**——不打断用户当前的任务流
2. 纠正完成后，**在回复末尾**简要评估是否需要沉淀经验
3. 如果需要，输出轻量建议（不超过 3 条）

**输出格式**：
```
---
💡 **经验沉淀建议**

刚才的纠正揭示了一个可沉淀的模式：

- **错误模式与证据**：[简述 AI 犯的错及文件或对话证据；严重度]
- **根因与类型**：[根因类别；机械可判定 / 需要判断]
- **建议与目标**：[具体操作；目标文件及执行或读取入口]
- **验证**：[违规／合规样例，或判断类回顾方式及局限]

是否需要我执行？（回复「沉淀」执行，或忽略继续当前工作）
```

**设计原则**：
- **不打断**：建议附在回复末尾，不影响正常工作流
- **轻量化**：仅简述，不展开长篇分析
- **建议优先**：不自主执行，等用户确认

### 模式二：手动触发（/reflect）

**触发条件**：用户通过 `/reflect` Command 主动发起。

**行为**：
1. 回顾当前对话历史
2. 识别被纠正的错误模式，并读取 [手动环境扫描](reference/manual-retro-scan.md)，检查七类环境问题；没有纠错记录也可扫描
3. 对有证据的错误和环境发现执行完整的诊断闭环；不可读取的材料标记为「未核验」
4. 先按严重度、再按影响范围排序，输出结构化的沉淀建议；无有效发现时明确 no-op，不制造规则

## 核心闭环

无论自动还是手动触发，共享同一个核心流程：

### Step 1: 识别错误模式

回顾对话中 AI 被纠正的场景，提取：
- **错误输出**：AI 说了什么/做了什么
- **正确方向**：用户期望什么
- **差距**：AI 为什么偏离

手动环境发现不要求有用户纠错，记录实际阻力、预期行为及文件或运行证据即可，不虚构对话。

### Step 2: 诊断根因

| 根因类别 | 定义 | 典型表现 |
|----------|------|----------|
| **规范缺失** | 现有 Rules/Skills 中没有覆盖该场景 | AI 不知道项目的特定约定 |
| **知识缺失** | AI 缺少项目特定的领域知识 | AI 对某个模块的行为/限制不了解 |
| **流程遗漏** | Workflow Skill 中缺少关键步骤或检查点 | AI 跳过了应有的验证步骤 |
| **模式错误** | AI 应用了错误的思维模式 | AI 用类比代替第一性原理推导 |

再独立判定违规类型，不能仅凭根因类别决定写规则：

| 违规类型 | 判定与动作 |
| --- | --- |
| 机械可判定 | 固定句式、禁用 API、import 形状、文件位置等有明确通过／失败条件：优先建议 linter、自定义检查、pre-commit、CI 或 hook，写明实际执行入口和验证方式 |
| 需要判断 | 依赖业务语义、设计取舍或上下文：建议规则、Standards 或 Skill 检查点，不把主观判断伪装成可靠的机械检查 |

混合问题拆开处理。机械检查暂不可行时记录限制和待办；临时文字提醒不能宣称已具备自动护栏。

### Step 3: 检索现有知识

定向搜索相关 Skills、Rules、Standards 和自动检查配置：
- 已有规则或检查？先核对适用范围、调用入口与实际运行证据，不直接追加同义规则。
- 已有检查却漏过违规？核验是否接入实际工作流、覆盖目标路径、正确传播失败退出码，是否被跳过或静默失效；优先修复接线或覆盖缺口。
- 完全没有护栏？作为缺口记录，再按违规类型提出新增建议；不能把「没有检查」记为通过。

检查文件存在不代表生效。无法安全复现时标记「未核验」，不以成功口头断言替代证据。

### Step 4: 生成建议

每条建议包含：

````markdown
### 建议 N: [简短标题]

- **根因**：[规范缺失 / 知识缺失 / 流程遗漏 / 模式错误]
- **违规类型**：[机械可判定 / 需要判断]
- **证据与严重度**：[文件位置或运行证据；按现有项目标准分级]
- **目标文件与入口**：`[检查配置 / Standards / Rule / Skill 路径]`；[如何被执行或读取]
- **操作**：[新建 / 在 X 位置添加 / 修改 Y 内容]
- **验证**：[违规样例失败、合规样例通过；判断类说明回顾方式及局限]
- **具体内容**：
  ```
  [要添加或修改的具体文本]
  ```
````

**建议数量**：≤ 3 条。多于 3 条时，先按严重度、再按影响范围取 Top 3，简述其余发现数量。自动建议保持轻量，上述字段可合并表述。

**落位**：确定性约束进检查及其接线；编码标准进项目 Standards 或对应 `std-*` Skill；操作流程进 Workflow Skill；领域知识按 `project-knowledge` 落位。全局 `CLAUDE.md` / `AGENTS.md` 仅保留每会话必需事实与导航指针，同一规则维护一个正文来源。编码标准的语义审查复用 `workflow-code-review` 的工程规范维度，不在此新建 Review 流程。

### Step 5: 用户确认

```
以上是本次经验沉淀建议，请选择：
- **全部执行** → 我将依次执行所有建议
- **选择执行** → 告诉我执行哪几条（如「执行 1 和 3」）
- **跳过** → 不执行任何建议
```

### Step 6: 执行更新

用户确认后，仅执行选中的建议。涉及代码或检查脚本时进入 `workflow-code-generation`，机器验证沿用 `workflow-verification`；规则更新检查读取入口与重复项。对确定性检查用违规／合规样例验证，并确认实际入口可传播失败；未完成时如实保留待办，不宣称护栏已生效。

## 强制规则

| 规则 | 说明 |
|------|------|
| **建议优先** | 检查、配置、Rules/Skills 的新增和修改都必须经用户确认；扫描不等于写入授权 |
| **不打断** | 自动触发时，建议附在回复末尾，不打断当前工作流 |
| **轻量化** | 自动触发时，建议控制在 3 条以内，每条不超过 5 行 |
| **可追溯** | 每条建议标注根因、违规类型、证据、目标及验证方式 |
| **不重复** | 执行前检索现有规则与检查，优先修复失效护栏，不重复堆叠规则 |

---

## 反模式

| ❌ 错误做法 | ✅ 正确做法 |
|------------|-----------|
| 被纠正后立即修改 Rules/Skills | 先完成当前任务，再提建议 |
| 输出冗长分析 / 建议过于宽泛 | 自动建议每条 ≤ 5 行；手动建议具体到证据、落位和验证 |
| 自主执行变更 / 打断工作流 | 等用户确认；附在回复末尾 |
