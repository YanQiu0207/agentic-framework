# 决策记录格式与提议条件

提议保存决策理由（ADR）时按本文件执行。条件与格式改编自 Matt Pocock `ADR-FORMAT.md`，资料基准为 `5beb35b040e3de97e54fa9e386d7e42d15c295c2`；落点以本框架知识合同为准，不新建平行 ADR 目录。

## 何时提议

三条同时满足才提议，缺任何一条就跳过：

1. **难以逆转**：事后改主意的代价有意义。
2. **脱离上下文令人意外**：未来读者看到会问「为什么这么做？」
3. **真实权衡的结果**：存在真正的备选，且因具体理由选了其一。

容易逆转的决策跳过，反正会改；不令人意外就没人会问为什么；没有真实备选就没有「我们做了显而易见的事」之外可记的内容。

够格的典型场景：架构形状（单体、事件溯源等）、上下文间集成模式（域事件而非同步 HTTP）、带锁定的技术选型（数据库、消息总线、认证提供方等换掉要一个季度的）、边界与范围决策（显式的「不做什么」也算）、刻意偏离常规路径（手写 SQL 而非 ORM）、代码中看不见的约束（合规限制、性能红线）、非显而易见的被拒备选（选 REST 弃 GraphQL 的微妙理由）。

## 极简格式

```md
# {决策的一句话标题}

{一到三句话：背景是什么、决定了什么、为什么。}
```

单段落即可。价值在记录「做了这个决定以及为什么」，不在填满章节。以下可选小节只在真有价值时加，多数决策不需要：

- **Status**（`proposed | accepted | deprecated | superseded by <编号>`）：决策可能被重议时有用。
- **备选方案**：被拒备选值得记住时才写。
- **后果**：有不明显的下游影响时才写。

## 本框架落点

- 本次取舍及理由写入当前 Change 的 `design.md`，这是既有设计合同的默认义务，不依赖三条件。
- 三条全中、值得长期保留时向用户提议沉淀；获批后长期有效的同步到相关业务域或模块的 `custom/decisions.md`，跨端工程决策写入对应 `engineering/tech/`。
- 不新建根目录或平行的 ADR 目录；仓库既有 `docs/adr/` 已标记停止写入，只保留迁移前来源。
