# 领域建模

开始前加载 `project-knowledge`，遵循其中 §3.4 的共享模型读取、§5 的唯一位置及 §7.1 的双轨写入规则。模型属于项目，由多个 Change 共享，不能只留在当前对话或 Change。

## 打磨模型

1. 在解释用户的领域用语或作出相关设计决定前，按知识索引读取相关术语与模型，再叠加本次 Change 已批准的差异。已有明确含义直接复用，不让用户重新解释。
2. 发现一词多义、同义词冲突或概念职责不明时，指出具体歧义，结合业务上下文确认规范含义。不同上下文同名概念不强制合并。
3. 用具体场景和边缘情况检验概念关系、领域边界、不变量及流程；不要只编制词汇清单。
4. 用户陈述涉及当前实现时，回到代码、Schema、配置、测试或运行证据核对。区分业务要求、当前实现与未来目标；矛盾按知识合同报告，不自动判定用户或代码错误。
5. 按知识合同分类后及时保存获授权的已确认内容。确认含义不等于授权写入；未来变化不能借「澄清术语」提前覆盖共享模型。无授权、分类不明或冲突未决时，仅在对话或当前 Change 保留候选。

## 记录边界

- 术语表只保留项目上下文特有的紧凑定义、别名及歧义，不混入实现细节、规格或全部会话记录。
- 概念职责、关系、业务规则与流程按知识合同分别归位；不新增根目录 `GLOSSARY.md`、平行 ADR 目录或占位模型。
- 本次设计取舍及理由记录在已有 Change 的 `design.md`。同时满足「难以逆转、脱离上下文令人意外、真实权衡」时重点提议保存理由；不满足这三项也不能省略现有设计合同要求的记录。
- 需要长期保留的决策依知识合同晋升，未批准目标不伪装成当前事实。写入许可不扩展为实现或外部操作许可。
- 用户暂停或撤销写入授权时立即停止，列出已写入内容与候选；不自动清理或删除历史文件。
