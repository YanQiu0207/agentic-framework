<a id="prototype"></a>
# 原型

原型是**用来回答一个问题的一次性代码**。问题决定形式。

<a id="pick-a-branch"></a>
## 选择分支

根据用户提示、周围代码，或用户在线时直接询问，确定要回答的问题：

- **「这套逻辑／状态模型感觉对吗？」** → [LOGIC.md](LOGIC.md)。构建一个可分享的独立 HTML 文件（自由操作按钮，加上按标签页组织的引导演示），让状态机经历难以只在纸上推理的场景，并让非开发者也能操作。
- **「它应该长什么样？」** → [UI.md](UI.md)。在同一个路由上生成几种截然不同的 UI 变体，通过 URL 查询参数和底部悬浮栏切换。

两个分支产出的工件非常不同，选错就浪费整个原型。如果问题确实模糊，且联系不到用户，默认选择与周围代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这一假设。

<a id="rules-that-apply-to-both"></a>
## 两个分支都适用的规则

1. **从第一天起就按一次性代码对待，并明确标记**。原型代码放在实际使用位置附近（被原型验证的模块或页面旁），使上下文清楚；命名应让随手看到的人也知道这是原型，而不是生产代码。一次性 UI 路由遵守项目既有路由约定，不要发明新的顶层结构。
2. **启动极其简单**。UI 原型通过项目任务运行器中的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示则是用户双击就能打开的单个 HTML 文件。无论哪种，启动都不应需要思考。
3. **默认不持久化**。状态保存在内存中。持久化是原型要*检验*的东西，而不应成为原型的依赖。如果问题明确涉及数据库，就用临时测试数据库或本地文件，并使用清晰的「PROTOTYPE, wipe me」名称。
4. **跳过打磨**。不写测试，不加让原型*能运行*之外的错误处理，不做抽象。目的就是快速获得认识。
5. **把状态展示出来**。逻辑原型每次动作后、UI 原型每次切换变体时，都打印或渲染完整的相关状态，让用户看见发生了什么变化。
6. **完成后保留证据**。将验证过的决策吸收到正式代码中，再把原型本身作为**一级来源**保留：提交到独立于 main 的一次性分支，在实现工单上留下指向该分支的上下文指针。同时将答案（结论及其解决的问题）记录到工单或提交中。主分支只保留已验证的决策。
