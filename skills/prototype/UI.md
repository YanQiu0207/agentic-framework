<a id="ui-prototype"></a>
# UI 原型

在单个路由上生成**几种截然不同的 UI 变体**，通过底部悬浮栏切换。用户在浏览器中逐个查看，选一个（或从每个方案借一些部分），再丢弃其余方案。

如果问题关于逻辑／状态，而不是外观，就选错了分支。请用 [LOGIC.md](LOGIC.md)。

<a id="when-this-is-the-right-shape"></a>
## 何时适合这种形式

- 「这个页面应该长什么样？」
- 「定下来之前，我想看看这个仪表盘的几种方案。」
- 「试试设置页面的另一种布局。」
- 任何否则会让用户花一天时间，在头脑中三个模糊模型之间挑选的情况。

<a id="two-sub-shapes-strongly-prefer-sub-shape-a"></a>
## 两种子形式：强烈优先选择 A

UI 原型**紧挨着应用其他部分**时，容易判断得多：真实页头、真实侧边栏、真实数据、真实信息密度。独立的一次性路由处于真空中，每个变体单独看都不错。只要有合理的现有页面可承载变体，就默认选择 A。只有原型确实无处安放时，才用 B。

<a id="sub-shape-a-adjustment-to-an-existing-page-preferred"></a>
### 子形式 A：调整现有页面（优先）

路由已经存在。变体渲染在**同一路由**上，通过 `?variant=` URL 查询参数控制。已有的数据获取、参数和认证都保留，只切换渲染。这是默认选择；除非有明确理由，否则就选它。

如果原型针对的东西还没有页面，但*自然应属于某个页面内部*（仪表盘的新区域、设置页的新卡片、现有流程的新步骤），仍然属于 A。把变体挂载到宿主页面内。

<a id="sub-shape-b-a-new-page-last-resort"></a>
### 子形式 B：新页面（最后手段）

只有被验证的东西确实没有现有页面可以容纳时才使用，例如全新的顶层界面，或无法合理嵌入任何现有位置的流程。

遵循项目既有路由约定创建**一次性路由**。不要发明新的顶层结构。命名要明显看出是原型（例如路径或文件名中带 `prototype`）。仍采用 `?variant=` 模式。

决定采用 B 之前，再确认：真的没有现有页面能嵌入它吗？空白路由会隐藏一些设计问题，而内容充实的页面会把它们暴露出来。

两种子形式使用相同的底部悬浮栏。

<a id="process"></a>
## 流程

<a id="1-state-the-question-and-pick-n"></a>
### 1. 说明问题并选择数量 N

默认 **3 个变体**。超过 5 个就不再是截然不同，而开始变成噪声，因此最多 5 个。

在原型所在位置或文件顶部注释里，用一行写明计划：

> 「设置页的三个变体，通过 `?variant=` 切换，位于现有 `/settings` 路由上。」

无论用户是否在线提出异议，这样都有效。

<a id="2-generate-radically-different-variants"></a>
### 2. 生成截然不同的变体

起草每个变体。每个都遵守：

- 页面目的及其可访问的数据。
- 项目的组件库／样式系统（TailwindCSS、shadcn、MUI、原生 CSS 等）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**：布局不同、信息层级不同、主要交互方式不同，不只是换颜色。三种略调后的卡片网格不是 UI 原型，而是壁纸。如果两份草稿过于相似，就明确要求「不要使用卡片网格」，重做其中一个。

<a id="3-wire-them-together"></a>
### 3. 连接各变体

在路由上创建一个切换组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于 A（现有页面）：保留切换器上方全部已有数据获取逻辑，每个变体只改变渲染子树。

对于 B（新页面）：在 `/prototype/<name>` 下的一次性路由中，挂载同样的切换器。

<a id="4-build-the-floating-switcher"></a>
### 4. 构建悬浮切换器

在屏幕底部居中放一个固定定位的小栏，包含三部分：

- **左箭头**：切到上一个变体（首尾循环）。
- **变体标签**：显示当前变体键；如果变体导出了名称，也显示名称，例如 `B (Sidebar layout)`。
- **右箭头**：切到下一个变体（首尾循环）。

行为：

- 点击箭头更新 URL 查询参数（使用框架路由器，例如 Next 的 `router.replace`、React Router 的 `navigate` 等），使变体可通过链接分享，刷新后也保持不变。
- 键盘：`←` 与 `→` 方向键也能切换。焦点位于 `<input>`、`<textarea>` 或 `[contenteditable]` 时，不要拦截方向键。
- 视觉上与页面区分（例如高对比度胶囊形、轻微阴影），让人明显看出它不是被评估设计的一部分。
- 生产构建中隐藏：以 `process.env.NODE_ENV !== 'production'` 或同等条件控制，避免误合并原型时将此栏发布给用户。

将切换器放在单个共享组件中，使两种子形式都能复用。位置遵循项目共享 UI 的存放方式。

<a id="5-hand-it-over"></a>
### 5. 交给用户

明确提供 URL（及 `?variant=` 的各个键值）。用户有空时会逐个切换。最有价值的反馈通常是**「我想要 B 的页头，加上 C 的侧边栏」**，那才是他们真正想要的设计。

<a id="6-capture-the-answer-and-clean-up"></a>
### 6. 记录答案并清理

选定变体后，记录答案（哪个变体，为什么），再按 [SKILL](SKILL.md) 的说明保留原型。把胜出方案吸收到真实代码，其余移到一次性分支，而不是 main：

- **子形式 A**：将胜出方案吸收到现有页面，从 main 移除落选变体和切换器。
- **子形式 B**：将胜出变体提升为正式路由，从 main 移除一次性路由和切换器。

整套变体是一级来源，因此应进入一次性分支，而不是垃圾桶。留在主分支中的变体组件和切换器很快会腐化，让下一个读者困惑。

<a id="anti-patterns"></a>
## 反模式

- **变体只在颜色或文案上不同**。那是微调，不是原型。真正的变体会在结构上作不同选择。
- **变体之间共享过多代码**。共享 `<Header>` 没问题，共享 `<Layout>` 就失去了意义。每个变体都应能自由推翻布局。
- **把变体连到真实写入操作**。只读原型没问题；如果需要写入，就指向桩实现。问题是「应该长什么样」，不是「后端能不能工作」。
- **直接把原型提升到生产环境**。变体代码是在原型约束下编写的（没有测试，错误处理最少）。吸收到正式代码时，认真重写。
