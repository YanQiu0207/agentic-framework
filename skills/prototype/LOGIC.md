# 逻辑原型

一个独立完整的 HTML 文件（**可分享演示**），让任何人都能通过点击按钮驱动状态模型。问题涉及**业务逻辑、状态转换或数据结构**时使用：这些东西在纸上看似合理，只有放进真实场景走一遍，才会感觉不对。

因为只有一个文件，无需安装，你可以交给非开发者（设计师、产品经理、领域专家），让他们亲自感受模型。因此，它应使用他们的语言，而不是代码的语言。

<a id="when-this-is-the-right-shape"></a>
## 何时适合这种形式

- 「我不确定这个状态机能否处理先 X 再 Y 的边缘情况。」
- 「这个数据模型真的能表示……这种情况吗？」
- 「写 API 之前，我想先感受一下它应该是什么样。」
- 任何想**按按钮、观察状态变化**的情况。

如果问题是「它应该长什么样」，就选错了分支。请用 [UI.md](UI.md)。

<a id="process"></a>
## 流程

<a id="1-state-the-question"></a>
### 1. 说明问题

写代码之前，先说明要用原型验证哪个状态模型、哪个问题。在演示顶部写一段话（用户可见的介绍，不只是注释）。回答错问题的逻辑原型纯属浪费，因此要把问题说清，让用户无论正在观看，还是离开后回来，都能核查。

<a id="2-isolate-the-logic-in-a-portable-module"></a>
### 2. 将逻辑隔离为可移植模块

将实际逻辑（真正回答问题的部分）放在单个 `<script>` 块中，写成一个小型纯模块，使它之后能被直接抽出、放入真实代码库。外围页面是一次性的，这个模块不是。

合适的形式取决于问题：

- **纯 reducer**：`(state, action) => state`。动作是离散事件、状态是单个值时适用。
- **状态机**：显式状态与转换。当「当前到底允许哪些动作」本身就是问题的一部分时适用。
- 针对普通数据类型的**一小组纯函数**。没有隐含当前状态、只有数据转换时适用。
- 如果逻辑确实拥有持续的内部状态，采用**方法接口清晰的类或模块**。

选择最适合所问问题的形式，*不是*最容易接到页面上的形式。保持纯粹：没有 DOM、没有 `document`，也没有按钮处理函数伸进内部。页面调用模块，反方向没有依赖。这让原型在自身使命结束后仍有价值：问题得到回答，验证过的 reducer／状态机／函数组可以独立移入真实模块。

<a id="3-build-the-shareable-html-file"></a>
### 3. 构建可分享的 HTML 文件

一个文件，原生 HTML／CSS／JS：没有框架、没有打包器、没有服务器；全部内联，双击就能打开，也能经邮件转发而保持可用。任何人打开它就应能运行。

面向非开发者编写。每个标签都使用**领域语言**，不是代码：按钮和状态读起来像业务，而不是 reducer。用平实语言解释正在发生什么。

从上到下，以清晰层级布局：

1. **标题和一句话说明**，解释演示让人探索什么（第 1 步的问题）。
2. **当前状态**：把完整相关状态渲染成可读面板（带标签的字段，而不是直接倾倒 JSON），每次点击后重新渲染，使变化可见。如果能帮助非开发者理解，就指出刚刚改变了什么。
3. **自由操作按钮**：每个动作一个按钮，始终可用，让人按任意顺序探索模型。每次点击派发对应动作，并重新渲染状态。
4. **引导演示**：一组**场景**，每个场景一个标签页。每个标签页先用简短、平实的文字描述场景（设置的情境，以及应观察什么），再列出该场景中按顺序**需要点击的按钮**。每一步都是真正的按钮：点击即执行动作，并进入下一步。开始演示时重置为已知初始状态，让每次运行场景都一致。

选择能展示棘手情况的场景，也就是难以仅在纸上推理的情况：正常路径、复杂边缘情况、尝试做一件本不应允许的事。

保持美观但克制：清晰排版、充足留白、一种强调色。没有动画，没有花招，不让任何东西与状态和按钮争夺注意力。

<a id="4-hand-it-over"></a>
### 4. 交给用户

把文件发给他们，或替他们打开。等他们有空，就能点击引导演示、自由探索。真正有价值的时刻，是他们说「等等，这不该发生」或「咦，我以为 X 会不一样」时：那是*想法*中的 Bug，正是原型的目的。如果他们想增加动作或场景，就添加。原型会演进。

<a id="5-capture-the-answer-and-the-prototype"></a>
### 5. 记录答案并保留原型

原型回答了问题后，先记录答案，再按 [SKILL](SKILL.md) 的说明保留原型。逻辑分支的具体对应方式是：验证过的 reducer／状态机／函数组移入真实模块（决策被吸收）；HTML 外壳随原型一起进入一次性分支，作为一级来源保留。由于是独立完整的单文件，在那里也始终很容易重新运行。

<a id="anti-patterns"></a>
## 反模式

- **不要添加测试**。需要测试的原型已经不再是原型。
- **不要连接真实数据库**。除非问题明确关于持久化，否则使用内存状态。
- **不要泛化**。没有「如果以后想支持 X 呢」。原型只回答一个问题。
- **不要将逻辑与页面混在一起**。纯模块一旦引用 DOM、`document` 或按钮处理函数，就无法直接抽离。页面保持为纯模块之上的薄壳。
- **不要使用框架、打包器或服务器**。收件人只需双击一个文件；React 应用或开发服务器会破坏「可分享」这一点。
- **不要把 HTML 外壳发布到生产环境**。页面针对人工点击演示而优化，背后的逻辑模块才是值得保留的部分。
