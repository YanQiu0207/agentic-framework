# 存量架构改善

本入口只读调查与讨论。默认在对话中给出 Markdown 报告；不写报告文件、不创建 Change、不更新知识或代码。用户明确要求保存时再确认目标与范围，按项目知识合同写入，不覆盖已有文件。

## 确定范围

1. 加载 `project-knowledge`，从 `openspec/index.md` 定向读取相关术语、约束及决策，再用代码与测试核实现状。无知识索引时说明缺口后调查代码，不自动初始化。
2. 用户指定模块或痛点时以此为范围；否则查看近期版本历史，优先调查反复修改的区域。Git 可用 `git log -n 50 --name-only --format=oneline`；其他版本控制使用其已有只读历史能力。没有历史或无法判定热点时说明限制，请用户圈定范围，不猜测热点或扫描整个仓库。
3. 加载 `bp-component-design`，读取其 `reference/deep-modules.md`。追踪范围内代表性调用者、完整行为、失败路径及测试；需要跨范围追踪时说明原因，明显扩大范围则先与用户确认。

## 调查与报告

找实际阻力：理解一个行为需跨多个模块跳转、调用者重复协调规则、接口泄漏内部状态、修改扩散或现有接口难以验证。深度判断使用共享方法，不按文件大小或抽象层数打分。

对每个候选提供：

- 涉及文件、调用链及测试的 `path:line` 证据，区分事实、推断和证据缺口。
- 当前阻力、触发它的具体变更场景；用删除检验检查是否只是透传层。
- 修改前后结构（简图或 Mermaid）、拟收进模块的行为及继续保留的内部职责。
- 预期减少的调用方知识、修改扩散与测试成本；不能只说「更优雅」。
- 迁移范围、兼容及失败恢复风险、现有测试保护、尚需验证的假设。
- 建议强度：优先处理／值得探索／证据不足；与既有决策冲突时展示双方证据与重议理由，不静默绕过决策。

仅报告有证据的少量候选，说明首要建议与保持现状的权衡。允许结论为「当前没有值得调整的候选」，不为凑数量制造问题；架构偏好不自动成为 P0／P1 或交付阻塞项。

## 用户选择与交接

报告后询问用户想深入哪项；未选择前停止，不自行设计详细接口或修改代码。

选中后讨论目标、约束、模块形状、测试接点和迁移风险，复用已确认答案；选择候选只授权讨论，不等于批准实现。明确记录未决问题及既有决策冲突。领域术语与决策按 `project-knowledge` 维护唯一来源，不新建根目录术语表或平行 ADR。

用户明确要求实施时，将已确认结论交给 `workflow-code-generation` 路由，复用适用的 Change 与批准；缺失设计或任务批准仍走既有流程。高风险架构变更走完整需求与系统设计，不以本入口绕过批准、验证、统一最终 Review 或知识归档。不自动安装工具、执行测试、切分支、提交或启用 Runtime。
