# 组件设计

> **使用场景**：`/system-design` 设计模块职责、接口、数据模型、并发或错误处理时加载（对应 `design.md` §4.3 对外行为与 §4.4 实现要点）。

## 第一性原理

> **组件设计的本质**：把架构方案转化为可实现的代码结构，定义清晰的职责边界和交互契约。

---

## 核心类/模块设计

设计或重组模块职责、接口及测试方式时，读取 [深模块与测试接点](reference/deep-modules.md)，检查调用方认知成本、复杂性局部性和接口可验证性。不要将职责单一误解为文件越小越好；本方法也适用于相关代码 Review。

### Checklist

- [ ] 类职责是否单一清晰？
- [ ] 继承层次是否合理（不超过 2-3 层）？
- [ ] 依赖是否指向抽象而非具体实现？
- [ ] 模块边界是否明确？

---

## 接口设计

> **接口设计关注对外暴露的 public API**，内部接口在「核心类/模块设计」中定义。

### Checklist

- [ ] 接口是否最小化（不暴露不必要的方法）？
- [ ] 参数和返回值是否清晰定义？
- [ ] 错误码是否完整列出？
- [ ] 线程安全性是否说明？
- [ ] 是否考虑了向后兼容？

---

## 数据模型

> **何时需要**：涉及数据存储、Schema 变更、新增数据结构时。

### 设计要素

| 要素 | 需要明确 |
|------|----------|
| **Schema** | 字段定义、类型、约束 |
| **索引** | 查询模式决定索引设计 |
| **编码格式** | 序列化方式（protobuf/flatbuffers/自定义） |
| **存储位置** | 存哪里？生命周期？ |

### Checklist

- [ ] Schema 字段是否完整定义？
- [ ] 索引是否满足查询需求？
- [ ] 是否考虑了 Schema 演进？
- [ ] 迁移/回滚方案是否明确？

---

## 并发模型

> **何时需要**：涉及多线程、异步操作、共享状态时。

### 设计要素

| 要素 | 需要明确 |
|------|----------|
| **线程模型** | 哪些线程？职责是什么？ |
| **共享状态** | 哪些数据被多线程访问？ |
| **同步机制** | 用什么锁？锁的粒度？ |
| **异步边界** | 哪里是同步/异步的边界？ |

### Checklist

- [ ] 线程模型是否清晰？
- [ ] 共享状态是否明确，保护机制是否合理？
- [ ] 是否有死锁风险？
- [ ] 锁粒度是否合适（不过粗也不过细）？

---

## 错误处理

> **何时需要**：涉及外部依赖、I/O 操作、可能失败的场景时。

### 设计要素

| 要素 | 需要明确 |
|------|----------|
| **失败模式** | 可能发生哪些错误？ |
| **错误表示** | 错误码 / 异常 / Status 对象？ |
| **重试策略** | 哪些错误可重试？退避策略？ |
| **恢复机制** | 失败后如何恢复到一致状态？ |

### Checklist

- [ ] 所有可能的失败模式是否列出？
- [ ] 错误表示方式是否统一？
- [ ] 可重试 vs 不可重试是否区分？
- [ ] 失败后的清理/恢复逻辑是否考虑？
