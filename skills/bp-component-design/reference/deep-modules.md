# 深模块与测试接点

设计或重组模块时，用以下问题判断复杂性是否真正减少，而不是按文件数量或代码行数评价设计。

## 判断方法

**模块**可以是函数、类、包或业务切片。**接口**是调用者正确使用它必须知道的一切，包括输入输出、调用顺序、不变量、错误、配置和必要的性能约束，不仅是类型签名。

**深模块**用较少的接口知识承载较多完整行为。内部仍可分解；「深」不是继承层数、实现行数或职责越多越好。

| 判断 | 检查方式 |
| --- | --- |
| 调用方认知成本／接口收益 | 列出调用者必须知道的规则；新接口是否减少这些规则，而不是只缩短函数名？ |
| 局部性 | 用一条真实的规则变更追踪调用点；知识、修改和验证能否集中，还是必须同步改动多个调用者？ |
| 删除检验 | 在推演中移除该模块：复杂性若消失，可能只是无价值包装；必要逻辑若散落回调用者，说明封装有价值。不得实际删除文件来做检验。 |
| 接口可验证性 | 关键行为能否从调用者使用的接口验证？若测试必须越过接口操作内部结构，先检查接口形状与职责归属。 |

候选建议需提供调用链或测试证据，并比较「保持现状」的成本；仅凭接口数量、目录层数或个人偏好不构成缺陷。

## 避免三种误判

| 案例 | 判断与动作 |
| --- | --- |
| 无规则的透传包装，只原样转发同样的参数和错误 | 若也无隔离、兼容或访问控制价值，可考虑移除；有这些职责时先核实，不机械删层。 |
| 校验、定价、库存等碎片由多个调用者重复协调 | 可将完整业务行为收进一个模块，对外提供简单结果；内部职责仍可分解，比较失败恢复与测试代价。 |
| 一个类混合订单规则、邮件模板与员工权限，变化原因互不相关 | 属于职责混杂，应按变化与所有权拆分，不能因外部只有一个方法就称为良好深模块。 |

## 选择测试接点

**测试接点**是可以控制输入、观察结果，必要时替换真实依赖的位置；不要求新增语言级接口或依赖注入框架。

1. 先列出行为、负责模块、已有可用接口及验证方式。优先用已有且能稳定验证该行为的较高层接口；不要把所有测试推到最昂贵的端到端路径。
2. 明确哪些外部依赖需要替换及原因，例如支付网络不可控；保留必要的真实集成验证，不能用全量 Mock 证明协作正确。
3. 新接点必须对应实际的变化或验证需求；只有一个实现并不自动否决接点，也不能为假想扩展预先增加抽象。
4. 重构前列出保留的行为测试和需迁移的实现耦合测试。先建立等效行为保护，再迁移旧测试；不因重构顺手删减覆盖。
5. 在设计或测试计划中记录「行为 → 模块／接口 → 替换依赖 → 正常、边界、失败证据」。适用时说明内部重组后应保持不变的测试。

本方法只提供设计判断，不新增批准门或 Review 严重度规则。
