# 系统设计

设计前加载 [project-knowledge](../project-knowledge/SKILL.md)，按 §3.1～§3.2 定向读取相关知识，按 §3.5 输出读取回执并在设计结果中说明采用依据。

## 核心定位

**AI 调研并提出设计方案，用户评审和决定。**

| AI 负责 | 用户决定 |
|---------|---------|
| 调研现有模块、接口、依赖和技术约束 | 设计方向和权衡取舍 |
| 提出具体方案，说明取舍、风险和放弃的备选 | 是否接受接口变更和模块划分 |
| 指出用户意见中的风险和矛盾 | 性能、可维护性等目标的优先级 |

**规则**：如果信息可以从 codebase 获取，**AI 必须自己调研**，不问用户。

### 提出方案与追问

加载 `bp-decision-interview`，按已确认需求和决策依赖推进。涉及领域语义时先加载 `project-knowledge` 并按 §3.4 读取共享模型；主动改变领域模型时加载 `bp-domain-modeling`，按同一知识合同记录，不另建术语与 ADR 目录。

- **先给方案**：前提已明确的决定，直接给出推荐方案及理由；存在实质不同的可行方向时列出备选和取舍。提方案前按 [规范加载](#规范加载按需) 加载对应规范。
- **只问用户才知道的事**：目标优先级、约束和偏好无法从需求或代码得出、且会改变方案时才追问；其余写明假设后继续。
- **推荐不等于批准**：方案经用户确认后才写入 design.md。用户提出自己的设计时，同样检查风险和遗漏，不直接附和。
- **第 6 节业界调研**：存在选型不确定性或缺少可靠依据时，AI 主动搜索业界方案，只写影响决策的结论；常规局部改动标注 N/A 并说明原因。

## 前置条件

- `proposal.md` 已存在且背景、目标、需求和验收标准完整
- `design.md` 不存在时，从 `reference/design_template.md` 复制创建；旧 `spec.md` 只允许迁移读取，不作为新写入目标
- **章节号约定**：design.md 保留历史局部编号 4～9，可与 proposal.md 的编号重叠，不重新编号。跨文件引用必须带文件名，例如「design.md §4.1」
- 如果不存在或不完整 → **停止，切换到 `workflow-requirements-clarification` Skill**

## 触发条件

- 用户说"开始设计"、"设计方案"
- `workflow-requirements-clarification` 完成后用户确认进入设计阶段

## 规范加载（按需）

**在讨论到相关 section 时才加载对应规范**，不要在开始时一次性加载所有规范：

| 规范 | 何时加载 |
|------|----------|
| `bp-architecture-design` Skill | 讨论 4.1 方案概览时加载 |
| `bp-component-design` Skill | 讨论 4.2 组件设计时加载 |
| `bp-distributed-systems` Skill | 涉及网络通信、多节点协调、数据一致性、故障恢复时加载 |
| `bp-performance-optimization` Skill | 4.3 核心逻辑完成后加载，优化性能方面的设计考量 |
| `workflow-test-generation` Skill | 讨论 7. 测试计划时加载 |

涉及模块职责、接口变更或重构时，加载 `bp-component-design` 并读取其 `reference/deep-modules.md`。先明确行为由哪个模块负责、调用者必须知道哪些规则，再选择测试接点；在 design.md 第 7 节记录行为、模块／接口、替换依赖及保留／迁移的测试。边界或接口决定代价高且方向不明时，按该参考的「接口候选并行探索」产出多个截然不同的候选后再纳入讨论。将这些决定纳入现有用户确认，不增加独立审批。实现与测试阶段复用已批准计划；契约冲突或范围变化返回受影响的设计决定，不把旧批准扩展到新行为。

## 对话模式

每轮处理一组前提已明确的决定：

1. 说明本轮要决定什么、涉及哪些 section
2. 给出推荐方案：做法、理由、放弃的备选和已知风险，区分事实、推荐与假设
3. 列出需要用户决定或补充的问题，等待回答
4. 按用户反馈调整，直到每项决定得到明确确认
5. 复述确认后更新 design.md

## 工作流程

### Step 0: 代码调研 + 需求摘要（AI 自主完成）

**目标**：理解现有实现 + 确认对需求的理解

**AI 操作**：
1. 读取 proposal.md 的需求章节
2. 先读 `openspec/index.md`，再按索引定向读取相关业务 Specs、共享契约、模块 `custom/`、历史 Change 和 `openspec/issues/`；AGENTS.md 已接线公共知识库时，仅在需要通用方法时查询其 `domains/`
3. 用代码、Schema、配置、测试或运行证据核实现状；知识与代码冲突时同时报告双方证据、版本和不确定性，不静默选择任意一方
4. 调用 `codebase-researcher` subagent 深度调研相关代码（模块结构、接口、依赖链、技术约束）
5. 生成摘要向用户确认
6. 用户确认调研摘要后，将报告追加写入本 Change 的 `research.md`（同需求阶段的落盘约定：按调研问题分节、沿用 `codebase-researcher` 报告结构、保留 `file:line` 引用；多次调研追加新章节，不覆盖旧章节）

**向用户汇报（必须）**：
```
我已读完 proposal.md 并调研了相关代码：

**需求理解**：
- 问题：[复述 proposal.md 中的问题]
- 目标：[复述目标]
- 关键约束：[复述非功能需求]

**代码调研**：
- 相关模块：[列出发现的模块]
- 现有接口：[列出相关接口]
- 技术约束：[发现的约束]

请确认我的理解是否正确？有遗漏或错误的地方吗？
```

**结束条件**：用户确认理解正确后才能进入设计讨论。已有明确确认的需求摘要与代码调研在范围未变时直接复用，不重复索取确认；新事实影响目标或范围时再展示差异并确认。

### Step 1: 提出方案概览

从 **design.md §4.1 方案概览** 开始，按「对话模式」给出整体方案：模块划分、依赖方向、数据流、与现有代码的关系和关键取舍。

### Step 2: 按决策依赖讨论、按 section 检查覆盖

独立且前提已明确的问题可适量分组，依赖未决答案的问题后置。章节用于归位内容与检查覆盖，不强制每轮一个 section；不在方案前提未确认时把下游结论当作最终方案。章节覆盖与写作边界参见 [reference/section-guide.md](reference/section-guide.md)。

section 不适用时，AI 说明理由并在 design.md 标注 `N/A - 本需求不适用`，随本轮内容一并请用户确认。

### Step 3: 更新 design.md

每个 section 完成后：
1. 复述本轮确认的决定，确认理解正确
2. 将**用户确认的内容**写入 design.md
   - 重要取舍按 `bp-domain-modeling` 的「讨论中的沉淀检查」及时记录决定、理由、备选及后果；命中时加载该 Skill，格式与长期晋升复用其记录边界。设计结束前核对遗漏，不等到交付才补记。
3. 更新 todo 状态
4. 进入下一组已就绪决定，设计结束前检查各适用 section 是否覆盖

## 强制规则

1. **AI 自主调研代码**：现有实现、接口等信息 AI 必须自己读代码获取
2. **设计前先确认理解**：展示需求摘要与代码调研结果并取得确认；已有有效确认不重复审批，范围变化重新确认
3. **AI 先提方案**：前提已明确的决定直接给出推荐方案、理由和备选，不反问用户思路
4. **只追问必要信息**：缺失信息只有用户掌握且会改变方案时才追问，其余写明假设后继续
5. **用户决定**：方案是建议，未经确认不得当作已批准设计；用户自己的设计意见同样检查风险
6. **按决策依赖提问**：独立问题可分组，依赖问题后置，不跨需求与设计阶段
7. **前提确认后形成结论**：章节不强制决定提问顺序；上游决定变化时复核受影响内容，未决假设不得写成已确认设计
8. **写作边界自检**：写入 design.md 前按 section-guide「写作边界」检查主位置、抽象层级和重复内容
9. **只记录确认内容**：design.md 内容必须是用户确认的

## 反模式

| ❌ 错误做法 | ✅ 正确做法 |
|------------|-----------|
| 问用户"现有实现是怎样的" | AI 自己读代码调研 |
| 直接开始设计讨论 | 先展示需求摘要 + 代码调研，确认后再开始 |
| 反问「你想怎么设计？」 | 直接提出方案，用户评审 |
| 生成设计后当作最终方案 | 用户确认后再写入 design.md |
| 用户说什么就同意什么 | 质疑潜在问题 |
| 4.1 讨论中写入具体调用点/函数签名 | 签名归 4.2；调用点留给任务拆解的 `context_files` |
| 同一决定在 4.1、4.4、第 5 节反复解释 | 在主 section 写一次，其他位置引用 |
| 上游决定未确认就把下游假设写成结论 | 按依赖推进，确认后将内容归位到对应章节 |

## 设计完成后

用户批准设计后，按 section-guide「写作边界」第 6 条定稿，再进入后续阶段。

**前端分支检查**：proposal.md 或 design.md 涉及前端 UI（新页面 / 新组件 / 用户操作路径 / `.tsx` 产物）时，进入编码前**先调用 `workflow-frontend-design`** 生成 `ui-spec.md`，再回到本流程。这与 `workflow-quick-design` 的前端分支对齐，避免到 `workflow-code-generation` 步骤 2 才因缺少 ui-spec 被动停下。

```
design.md 已完成。

你可以：
- 说"开始编码"进入 code generation 阶段（涉及前端 UI 时先走 /frontend-design 生成 ui-spec.md）
- 说"先写测试"进入 TDD 模式
- 如果某个 section 需要修改，告诉我具体哪个
```
