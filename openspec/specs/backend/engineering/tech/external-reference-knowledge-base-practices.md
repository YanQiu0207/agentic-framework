# 知识库建设实践：三篇文章提炼与框架借鉴建议

- 整理日期：2026-10-26。
- 状态：外部调研记录；归档导航已按用户授权试点，严格验收未通过，其余借鉴建议未实施；本文不构成现行框架合同。
- 调研方式：通过 `browser-act` 技能读取三篇文章正文，对照当前仓库的知识操作合同与相关校验代码。
- 证据边界：文章中的内部平台能力按作者描述引用，未独立验证；本次仅做文档与定向源码核对，未运行测试或验证全部运行路径。

## 1. 结论

当前框架已有知识分类、渐进读取、人工知识保护、Change Delta 与归档同步机制，不需要另建一套知识库。最值得补强的是：

1. **业务场景到技术实现的映射**：让 Agent 从用户操作找到入口、模块、数据、消息、外部影响与验证方法。
2. **知识实际采用情况的反馈**：区分「文件存在」「读过」「实际采用」「被当前证据支持」。
3. **复核与退役治理**：Change 2059 已补齐退役操作合同；后续重点是复核触发与执行效果，不再从零制定退役标记。

建议继续复用现有 `openspec/`、Change、索引与校验入口，暂不引入向量数据库、知识图谱、全库 YAML 化或自动成熟度平台。

## 3. 知识库应包含什么

以下是对三篇内容的综合分类，不是任何一篇的原始目录标准。

| 内容 | 要回答的问题 | 典型条目 | 来源定位 |
| --- | --- | --- | --- |
| 业务语义 | 需求里的词到底指什么？ | 概念、别名、非同义词、上下文、边界、规则、不变量 | A §3.2.1、§5.1；B §4 |
| 场景与技术映射 | 用户的操作实际经过哪里？ | 页面／操作 → API → 服务 → 数据 → 消息 → 下游 | A §5.1 |
| 系统与依赖事实 | 有什么能力，谁依赖谁？ | 职责、接口、数据所有权、同步／异步链路、强弱依赖 | A §3.2.2～3.2.3；B §1～3 |
| 约束与决策理由 | 哪些不能改，为什么？ | 兼容包袱、禁止操作、审批条件、历史方案取舍 | A §5.1、§5.3；B §4、§6；C §1.2 |
| 验证与操作方法 | 怎么改，怎么证明改对？ | 测试入口、迁移检查、Runbook、等待生效、回滚步骤 | A §5.3；B §5～8；C §2 |
| 知识治理信息 | 当前还能信吗，是否有用？ | 来源版本、适用范围、确认状态、使用记录、替代关系 | A §5.1、§5.3；C §1.6～1.8 |

A §6 建议优先显式化「高复用、高风险、高隐性」知识。C §1.2 强调阴性知识、代码位置索引、隐含关联关系。共同点是不重复解释一眼能从代码看出的实现细节。

例如，「这个字段不能删除，因为旧消费者仍在使用」比「这个函数有三个参数」更值得长期保留。

### 3.1 A 的业务层组织方式

A §5.1 给出的参考结构包括：

- `meta`：领域概念、别名、边界、关系与核心规则。
- `principle`：领域内跨场景复用的超时、一致性、降级、兼容等原则。
- `scenario`：业务操作与技术链路的映射。
- `practice`：历史设计、原因、风险与适用条件。
- `history`：知识库自身的生成、审核与变更日志，不保存知识正文。

文章明确说明这只是参考实践，不能把目录名或固定拆分数量当作所有团队必须遵循的标准。

## 4. 操作与流程

本节是综合归纳的生命周期，不是三篇共同实现的一套流水线。

### 4.1 建立：从最小地图开始

```text
选择真实且风险可控的业务域
    → 标出职责、核心链路、依赖和风险
    → 提取代码、Schema 和配置可确认的事实
    → 人工补充业务语义、历史原因和红线
    → 标记来源、确认状态和适用范围
    → 建立根索引与主题索引
```

依据：B §13 的试点路线；A §5 的分层落地。不要先要求覆盖全部服务或生成所有模板文件。

### 4.2 读取：导航后核实，再行动

```text
根索引
    → 相关主题／模块索引
    → 相关正文
    → 当前代码、配置、测试与运行证据
    → 影响面、约束和方案
    → 实现与验证
```

| 阶段 | 重点读取 |
| --- | --- |
| 需求 | 业务语义、场景和边界 |
| 设计 | 依赖、数据所有权、约束和历史决策 |
| 编码 | 兼容要求、禁止项与模块约束 |
| 验证 | 变更类型对应的检查和完成标准 |
| 排障 | 历史坑点、运行事实和 Runbook |

依据：A §2.3；B §6；C §1.1～1.4。知识应支持任务，但不能替代对当前事实的核实。

### 4.3 写入：任务复盘后定向补充

```text
回顾任务与验证结果
    → 筛选脱离本次任务仍然有用的知识
    → 查询已有条目，避免重复
    → 已有主题定点补充；没有才新建
    → 同步索引
    → 记录实际采用的知识及结果
```

C §1.5～1.7 强调不写过程流水账、不整篇覆盖已有文档；待验证猜测不能冒充确定结论。A §2.3 强调把评审遗漏、事故和隐性依赖反向沉淀。

### 4.4 维护：高频轻任务与低频重任务分开

| 高频轻操作 | 低频重操作 |
| --- | --- |
| 检查新增条目与索引 | 查重、消歧和主题整理 |
| 聚合新增使用记录 | 检查长期未复核条目 |
| 核对相关来源变化 | 处理过期、替代和归档 |
| 定点修改元数据 | 全库结构巡检 |

C §1.6～1.8 的核心是「机械动作增量执行，判断性整理低频执行」。其轻任务只提升成熟度，不做衰减；重任务才执行全库衰减，不能把两者混成每次任务结束都跑的全库扫描。

### 4.5 形成行动闭环

C §2 将知识使用连接到排查、编码、本地验证、提交／合入、等待生效、真实效果确认和复盘。等待必须绑定本次分支、构建或任务对象，直到成功、失败或超时，不能用「最近一次成功」替代本次结果。

这提供的是流程参考，不授予自动提交、合入、发布或访问生产环境的权限。

## 5. 注意点与不宜照搬的做法

### 5.1 区分事实、规范和猜测

「代码目前允许」不等于「业务允许」；模型推断的约束不等于组织确认的红线。A §5.3 使用 `confirmed: false` 表示未确认知识，提醒 Agent 不应将其作为已确认事实。

建议分别记录事实来源和规则确认来源，不让自动生成结果自行升级为强制规则。

### 5.2 使用频率不等于真实性

C §1.8 用实际采用次数和跨场景复用提升成熟度，并区分阅读弱信号与采用强信号。该机制可用于衡量复用价值，但不能直接证明正确性：

- 错误也可能被反复引用。
- 很少使用的安全红线仍需保留。
- 来源变化后，历史使用次数不能证明当前有效。

适配建议：将「验证状态」「使用频率」「新鲜度」分开，不照搬单一成熟度排序。采用声明本身也需要关联任务与验证证据，不能只靠 Agent 自报。

### 5.3 过期不等于删除

来源变化、长期未使用可以触发复核，不能直接证明业务约束失效。优先更新适用范围或标记被替代，维护替代链接与索引；删除仍须遵守项目既有授权与备份规则。

### 5.4 Hook 应有适用范围与恢复路径

C §1.4 描述了未读一级索引就拦截探索工具的 Hook。借鉴时必须解决：

- 读取索引本身的放行。
- 索引缺失、失效或工具故障时的明确处置。
- 换项目、子会话和知识更新后的重新判定。
- 轻量判定的性能成本。
- 「读过」不等于「理解并采用」的证据边界。

不建议直接拦截所有工具；先选择明确的工程入口试点，不把探索性研究套进完整交付门禁。

### 5.5 权限与环境口径必须明确

B §9 强调权限分级、脱敏和审计。C §2.2 提到禁止正式环境验证，但 §2.3 又使用「线上真实闭环验证」表述，环境与允许动作的口径存在张力，不能未经澄清直接转成框架规则。

知识阅读、候选生成、共享写入、公共库晋升、代码合入和生产操作是不同授权，不得相互替代。

### 5.6 不复制工具规模

A 描述的 KBase、aitom 和系统层 YAML 适合其团队场景，不是本框架必须引入的平台。应优先补信息与反馈链路，再按真实查询成本判断是否需要检索平台。

### 6.2 已有能力：保留而非重建

| 文章做法 | 当前框架合同 | 判断 |
| --- | --- | --- |

| 临时结论不直接进入长期知识 | §7 的 Change Delta 与归档同步 | 已有，保留验证前置 |
| 任务结束复盘 | §9 的 intent 沉淀检查 | 已有，可补使用反馈而非另建平行复盘 |
| 知识与当前事实冲突需报告 | §4 的双方证据与不确定性要求 | 已有，应继续保留 |
| 公共知识谨慎发布 | §1、§8 的确认与作用域边界 | 不照搬自动共享写入 |

### 6.3 机器保障的实际边界

`validate_change.py` 的 `_validate_archive_knowledge()` 检查知识影响、Delta 映射、同步状态、索引更新说明、冲突记录与实际 Diff 核对记录。其函数说明明确不做语义合并，因此不能据此证明正文已正确同步。

`knowledge_sync.py` 负责从镜像 Delta 路径反推长期目标、解析同步表，不负责判断知识内容真假。

`verify.py` 的 `knowledge_source_warnings()` 对来源版本、路径与提交关系进行检查，产生非阻塞告警。设计记录 §10 也明确 Git 新鲜度检查不覆盖工作区未提交修改。因此不能将其描述成完整的过期内容检测或知识更新器。

## 7. 借鉴优先级与最小落地建议

除 §7.1 已授权的归档导航试点外，以下仍为候选，不表示已批准或已实施。

### 7.1 优先一：场景到技术实现映射

复用合同规定的 `flows.md` 位置与模块知识引用，不表示本仓库已有该文件。框架自身的工程归档流程先在现有知识管理模块概览补导航，不为试点制造业务域或平行目录。关键流程补齐：

> 业务操作、前置条件、入口、涉及模块、数据变化、异步事件、外部影响、失败处理、验证入口。

框架自身可先用「归档 Change」试点：从用户入口追到 Command、Skill、脚本、门禁、产物和失败停止点。适用信息分别留在其唯一位置，流程文档通过链接串联，不复制规则正文。

本次已授权试点：在知识管理模块概览补「归档 Change」导航；验收协议与结果见 [归档场景导航验收](../../../../acceptance/2026-10-26-archive-navigation.md)。由不继承本对话的只读 Codex 会话从根索引查找，主会话按四项问题及当前证据核对；不是正式归档执行或框架交付门验证。

### 7.2 优先二：知识实际采用记录

先在现有交付证据中试记三项，不立刻引入成熟度系统：

- 采用的知识路径。
- 用于哪个决策或检查。
- 当前证据支持、发现冲突或尚未验证，以及对应证据。

建议验收：可以区分「读过」与「采用过」，并能追溯一次知识冲突或有效复用；不强制为无相关知识的任务制造引用。

### 7.3 优先三：复核与退役流程

```text
来源变化／发现冲突／人工提出失效
    → 标记待复核
    → 核对证据与适用范围
    → 更新、保留或标记已被替代
    → 维护替代链接、索引和引用
```

最新核对基线为 `8a22aea2d90cb455eb298835cd3f063a71311dab`：Change 2059 已归档至 `openspec/changes/archive/2059-2026-10-26-knowledge-retirement-contracts/`，归档任务表两项 Delta 均标记已同步。现行操作合同 §7.3 已明确状态标记、人工确认、索引与引用维护及禁止自动物理删除；长期方案 §9.1 已引用 §7.3。原「部分知识类型尚无统一作废 SOP」为更新前快照，不再代表当前现状。

本节流程中的「待复核」是后续候选步骤，不是新状态枚举；后续只评估复核触发与执行效果，复用现行退役合同。

建议验收：旧知识不会继续作为无提示的现行建议被路由；历史原因和替代关系仍然可追溯；不发生未授权删除。

### 7.4 后续：选择性强化机器检查

在以上试点有证据后，再评估：

1. 对明确工程入口增加必要上下文接线或读取检查，区分规则要求和实际读取证据。
2. 将 API、Schema、状态机、消息契约等高风险变更接到对应验证要求，而非只检查测试说明是否填写。
3. 将增量索引维护与低频知识巡检分开，避免每次任务结束全库扫描。

建议验收：选择一个真实遗漏案例，证明检查能发现遗漏，也能正常放行无关任务，并明确故障恢复路径。

## 8. 本轮不做的事项

- 不修改现有 Skill、门禁、权限或知识分类合同。
- 不自动生成全库事实缓存，不全库迁移或改写。
- 不引入向量数据库、知识图谱或成熟度平台。
- 不按引用次数认定真实性，不按时间自动删除知识。
- 不写入跨项目公共知识库，不自动批准上述候选。

后续若决定实施，按现有 Change 流程明确范围、设计与验收。本文件仅保存调研结论与候选理由。
