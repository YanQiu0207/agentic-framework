## 4. 设计方案

### 4.1 方案概览

建议新增两个共享方法技能和两个薄命令入口，在现有需求与系统设计中按阶段复用，不另建工程状态机。

| 候选入口 | 职责 | 默认副作用 |
| --- | --- | --- |
| `/grill-me` | 通用计划或决定的压力测试 | 仅讨论，不写文件、不切工程阶段 |
| `/grill-with-docs` | 工程访谈与受控记录 | 先识别阶段、Change 和写入授权，不自动创建或选择 Change |
| 现有需求与设计命令 | 继续拥有阶段前置检查、产物及审批 | 按现有规则执行，仅复用共享方法 |

若工程入口没有已确认的 Change，涉及未来业务变化时只读讨论，需要落盘则转交既有需求流程确认编号与范围；仅澄清既有领域知识时可按 §4.2.6 单独取得共享模型写入授权，不强制创建功能 Change。若无完整需求，不得进入正式系统设计。

### 4.2 组件设计

#### 4.2.1 核心类或模块设计

| 候选文件 | 维护职责 |
| --- | --- |
| `skills/bp-decision-interview/SKILL.md` | 决策依赖、事实自查、分组提问、局部确认及有界收敛 |
| `skills/bp-domain-modeling/SKILL.md` | 术语澄清、场景检验、事实核对及知识路由 |
| `commands/grill-me.md` | 指定通用讨论模式并引用共享方法 |
| `commands/grill-with-docs.md` | 指定工程模式、阶段约束及授权检查，引用两个共享方法 |

入口只保留模式、路由与停止条件；方法保持单一来源。若确定性安装逻辑对技能或命令有枚举，实施时核对后再做必要接线，不能假设新增目录会自动发行。

#### 4.2.2 接口设计

访谈输入为目标、现有上下文、当前阶段、已确认决定、证据与写入授权。无需新增 JSON Schema 或公共 API。

每轮输出必要问题及其依赖；有建议时列出理由与重要替代选项。需求与系统设计的常规调用仍保留原有「未经请求不主动给方案」限制；用户显式调用新访谈入口时，才视为请求提供访谈建议，且需求阶段不得给实现方案。

每个答案按编号关联确认；不明确的「可以」不能批准本轮所有取舍。不得要求每一项机械细节都等待人工确认，优先复用已有授权。

#### 4.2.3 数据模型

决策状态仅为对话工作模型：未就绪、待回答、已确认、待调查、延期、非目标。不建立持久化调度器，不改变现有 tasks.md 或 Runtime DAG。

术语定义只包含项目上下文含义、歧义与必要禁用别名；实现细节写入设计。术语只是领域模型的一部分，概念关系、业务不变量和流程同样进入共享知识。写入时按 §4.2.6 区分既有知识澄清与未来变化，不将目标状态伪装成当前实现。

#### 4.2.4 并发模型

无新增运行时并发机制。调查可本地完成；仅在宿主支持且项目允许时委派，不因上游原文强制创建子 Agent。调查中只阻塞依赖其结论的问题，不阻塞独立问题。

#### 4.2.5 错误处理

- 无法查明事实：报告已查证据和缺口，标记待调查，不编造答案或让用户代查可获取事实。
- 知识、代码或用户描述冲突：展示双方证据，区分现状与目标，等待必要裁决，不静默覆盖。
- 无写入授权或目标位置不明确：只在对话中给候选记录，不创建文件。
- 用户暂停或结束：输出已确认决定与未决项，不继续写入或执行。已经授权并写入的内容如实列出，不擅自删除。
- 关键阻塞尚未解决：允许结束会话，但不声称已达成可实施共识。

#### 4.2.6 项目共享领域模型与读写生命周期

共享模型是跨 Change 的语义主本，不是当前实现的事实源；实现行为仍需代码、Schema、测试或运行证据核实。Change 只保存本次差异，不能成为查找基础业务定义的唯一入口。

| 内容 | 唯一建议位置 | 记录边界 |
| --- | --- | --- |
| 术语、别名、歧义与上下文限定 | `openspec/specs/business/glossary.md` | 同名概念按业务上下文区分，不强行统一含义 |
| 概念职责、关系及领域边界 | `openspec/specs/business/<domain>/overview.md` | 用文字或必要关系图说明，不要求新增图谱系统 |
| 业务规则、不变量与状态转换约束 | `openspec/specs/business/<domain>/rules.md` | 区分业务要求与当前实现是否满足 |
| 跨模块业务流程 | `openspec/specs/business/<domain>/flows.md` | 保存领域流程，不混入一次性实施步骤 |
| 本次拟议变化 | 当前 Change 中镜像以上路径的 `specs/` Delta | 未交付前不能当作所有 Change 的现行规则 |

读取链为 `openspec/index.md` → `openspec/specs/business/index.md` → 相关术语与领域条目。小项目允许根索引直接链接条目，不为满足层级创建空索引。

实施时在 `project-knowledge` 统一维护以下读取契约，两个新入口及需求、设计阶段显式接线；实现、测试、Review 的现有知识路由在涉及领域语义时复用该契约，不复制另一套目录规则：

1. 解释用户领域用语或作出相关设计决定前，先读取索引命中的共享术语和相关模型，再叠加本次 Change 的已批准差异。
2. 同一会话已读取且内容未变化时复用上下文；新会话或模型更新后重新读取相关内容，不重复询问已有答案。
3. 索引未命中时在知识合同允许范围内定向查找；确无知识才询问，不默认扫描全库或全部历史 Change。
4. 模型与代码不一致时展示双方证据，区分业务意图、当前实现和本次目标，不把任一方静默判为错误。

写入采用两条路径：

| 分类 | 前置条件 | 写入与同步时机 |
| --- | --- | --- |
| 既有知识澄清 | 用户明确确认既有含义、明确授权目标条目更新；可核实事实已核实，无未决冲突，不引入未来行为 | 读取原文后最小更新共享条目及索引，记录来源、确认日期和适用范围，不必等待功能交付 |
| 未来业务变化 | 拟新增或改变概念、规则、关系或行为 | 当前 Change Delta 保存目标；实施验证及归档同步后才晋升共享模型 |
| 尚无法分类或存在冲突 | 含义、证据、上下文或授权不完整 | 有 Change 则留其中候选；否则留对话待确认，不修改共享主本 |

「既有知识澄清」是对知识合同的新增明确分支，不是当前能力声明。用户确认含义不等于授权写入；若澄清实际改变业务语义，必须改走未来变化路径。无代码可核对的纯业务定义标明用户确认为来源，不伪称实现已验证。不得借此绕过 `custom/` 人工内容保护或公共知识晋升批准。

每次共享写入先读取最新目标条目，比较相关 Change Delta，定向检查受影响定义与引用；没有冲突才最小合并，并维护可达索引。未来规则不因另一个 Change 的讨论被提前晋升；已有澄清若被候选 Delta 覆盖则显式协调。这里只增加操作规则，不承诺文件锁或并发事务能力。

本期只实现这套能力，不为本框架虚构业务领域、不创建无内容的业务知识文件，也不批量迁移历史 Change。

### 4.3 核心逻辑实现

1. 复用当前请求、已有 Change 和对话答案，识别阶段与授权范围；涉及领域语义时，先按 §4.2.6 读取共享模型。
2. 区分可查事实和待用户取舍，建立仅覆盖当前目标的决策依赖。
3. 自查必要事实，将就绪问题按认知负担适量分组，不设置「必须问完整个前沿」硬约束。
4. 等待并关联用户回答；上游决定改变时重新检查下游结论，不能沿用失效批准。
5. 若开启工程记录，先分类为既有知识澄清或未来变化，按 §4.2.6 在授权范围写入共享模型或 Change Delta；候选、已批准目标与当前实现必须区分。
6. 当前范围关键决定明确且用户确认时收敛；其余问题列为待调查、延期或非目标。结束访谈不代表获准执行。

### 4.3.1 现有规则冲突裁决候选

| 冲突 | 拟议裁决 | 行为影响 |
| --- | --- | --- |
| 每轮一个核心问题与整批前沿 | 可分组独立问题，依赖问题后置；删除需求技能中相反的硬限制 | 改变提问节奏，必须行为评测 |
| 按章节顺序与决策依赖 | 章节作为产物覆盖检查，依赖作为提问顺序；不跨阶段 | 改变系统设计对话顺序 |
| 每题推荐与禁止未经请求给方案 | 常规调用保持既有限制；显式访谈入口允许阶段内建议 | 明确入口授权范围，不能扩展为实现授权 |
| 术语确认即写长期文档与 Change Delta | 既有澄清另获写入授权后及时更新；未来变化先 Delta，归档再同步 | 新增明确分类分支，保留确认、证据及归档要求 |
| 全分支穷尽与用户可停止 | 当前范围内有界收敛，显式标记未决项 | 不以提前结束冒充设计完成 |

上述均是待批准的行为调整，不以「表达精简」名义实施。未列出的安全、审批和验证规则保持不变。

### 4.4 方案优劣分析

- 优点：共享方法可用于需求和设计，不复制治理流程；沿用唯一知识路由。
- 代价：需要裁决既有对话约束并做行为回归，不能只跑文本校验。
- 风险：推荐答案可能造成锚定；批量提问可能增加认知负担；宽泛触发可能把普通讨论错误路由为访谈。
- 应对：说明替代项和不确定性、适量分组、明确近邻不触发场景、检查执行轨迹和副作用。

## 5. 备选方案

| 方案 | 判断 |
| --- | --- |
| 原样安装上游依赖链 | 不推荐；对话约束、知识目录及宿主调用机制需要适配 |
| 只改现有需求与设计，不加命令 | 改动较小，但无法满足独立通用访谈入口；可由用户选用 |
| 两入口加共享方法，复用现有治理 | 推荐候选；命名和接线经审核后确定 |
| 新建完整访谈状态机及 ADR 生命周期 | 本期不做；缺少用户需求，不引入额外系统 |

## 7. 测试计划

| 场景 | 观察与通过标准 |
| --- | --- |
| 独立与依赖混合问题 | 独立问题可同轮；依赖未决答案的问题不提前问 |
| 上游决定变更 | 重新确认受影响下游取舍，不沿用已失效答案 |
| 环境事实与未知事实 | 能自查则自查；证据不足明确未知，不编造 |
| 需求访谈与已有设计 | 不越界设计；上下文已有答案不重复问 |
| 术语歧义与代码冲突 | 给具体场景及双方证据，不自动决定谁错 |
| 只讨论、暂停、拒绝写入 | 观察文件快照与工具轨迹，禁止副作用为零 |
| 局部确认与含糊同意 | 只接受明确对应项，不批准整轮或开始实现 |
| 近邻请求 | 普通问答、直接编辑术语、快速设计不被强制改成完整访谈 |
| 工程记录与知识晋升 | 未来变化留在 Change，既有澄清经独立授权后可及时更新；含糊分类不能覆盖共享模型 |
| 跨 Change 与新会话复用 | A 的既有知识澄清已授权沉淀后，新会话 B 仅通过项目索引找到模型并正确理解术语，不依赖 A 的会话 |
| 同词多义与索引维护 | 按业务上下文区分同名概念，新增知识可从根索引到达，不破坏现有引用 |
| 并行 Change 修改同一概念 | 对照最新共享条目和相关 Delta，冲突被报告，未交付规则不会被当作当前共享定义 |
| 无冲突的既有知识澄清 | 核实来源并明确写入授权后最小更新共享条目；未授权只保留候选，业务定义不冒充代码事实 |
| 加载与发行 | 实际加载共享方法，安装后两入口可用；不能只检查引用字符串 |

实施后在 `validation.md` 保存固定输入、模型与宿主配置、工具权限、轨迹位置、预期与实际结果。对照原流程与候选流程运行代表性场景，报告需求遗漏、返工、人工轮次与副作用；单次成功不等于效果提升。

结构检查运行技能图、任务依赖及 Change plan 校验；行为检查失败则不推广。禁止副作用场景在隔离测试目录执行，不污染用户项目。
