# Proposal：重新裁决双 Profile 收敛边界

## 1. 问题

`framework-unification.md`（状态 Approved）在四处禁止 Production 与 Tooling 收敛为一条执行链：

| 位置 | 原文 | 行号 |
| --- | --- | ---: |
| §1 决策结论「明确不采用」 | 把 Production 与 Tooling 强行合成一条工作流。 | 27 |
| §1 决策结论「明确不采用」 | 把两套 Tasks 控制逻辑合成一个巨型状态机。 | 31 |
| §3.2 | 因此必须保留两个独立生命周期，只共享场景无关的工程能力。 | 94 |
| §8.1 | Production 校验器是只读生命周期裁决器；Tooling 控制器是有状态执行引擎。二者不能合并为同一个状态机。 | 299 |
| §19.1 放弃原因 | Production 和 Tooling 的 Artifact、人工介入和执行策略不同。 | 657 |
| §19.1 放弃原因 | 单一路由会持续积累条件分支，最终形成难以理解的巨型 Skill。 | 658 |

而当前的演进目标模型是：

> Tooling 是统一执行底座；Production 是按风险启用的治理升级策略，而不是第二套独立流程。同一任务只走一条执行链；当风险命中时，在 Tooling 的节点上叠加 Production 门，而不是切换到另一套 `opsx-*` 生命周期。

两者直接冲突。按 `AGENTS.md`「知识与当前事实冲突时，必须展示双方证据，不得静默选择或修改任意一方」，这个冲突必须先裁决，不能由后续每个 Change 各自绕过。

**本 Change 不重新论证是否应当收敛。** 目标模型是输入，由用户给出。本 Change 裁决的是：规格用什么结构容纳它，以及哪些边界必须保留。

## 2. 规格自身已经推翻了 §19.1 的第一条理由

§19.1 把「Artifact 不同」列为放弃收敛的首要原因。但同一份文件的两处已经否定了它：

| 位置 | 原文 | 行号 |
| --- | --- | ---: |
| §5.4 | 两个 Profile 的 Change 均位于 `openspec/changes/<ticket>-<change-name>/`……不能另建第二套 Artifact 根目录。 | 220 |
| §6.3 | Tooling 与 Production 使用相同的 `openspec/changes/`、`openspec/specs/` 和 `openspec/issues/` 契约；差异仅保留在审批、Review、DAG、Worktree、失败恢复和 Runtime 审计策略中。 | 258 |

§6.3 的措辞尤其关键：它已经把两轨差异**枚举**为审批、Review、DAG、Worktree、失败恢复、Runtime 审计六项，而这正是目标模型中「Production 升级项」与「Tooling 底座」的划分方式。

结论：§19.1 的第一条理由不是判断有误，而是决策演进后未同步的遗留措辞。§5.4 与 §6.3 是更晚的、更具体的裁决，§19.1 停留在合并初期。

## 3. 四处条文捆绑了两个不同的命题

三处禁令的表述把「差异是否存在」与「差异由什么承载」写在了同一句里：

| 命题 | 规格立场 | 目标模型是否否定 |
| --- | --- | --- |
| A 生命周期语义差异必须保留（人工介入点、执行策略、归档要求、Verification 失败策略、默认风险偏好） | 必须保留 | **不否定**，目标模型明确保留全部五项 |
| B 这些差异必须由两套独立实现承载 | 隐含必须 | **否定** |
| C 两套 Tasks 控制逻辑不能合并为一个状态机 | 不能合并 | 部分否定，需按层拆分 |

§3.2 列举的五项差异（`framework-unification.md:88-92`）在目标模型中一项都没有被删除，它们从「两条流水线的固有属性」变成「按 Profile 声明的策略参数」。语义强度不变，承载方式变化。

命题 A 与命题 B 被捆绑表述，导致任何触碰承载方式的改动都会形式上违反 §3.2，即使它完整保留了语义差异。这是本 Change 要拆开的东西。

## 4. 结构缺陷：无条件否决无法被证据更新

同属第 8 章的 §8.2 是**条件式否决**：它给出三条重新评估条件（`framework-unification.md:305-309`），change 2035 已逐条举证全部满足，于是提取公共 AST 成为规格内部允许的动作，不需要推翻任何条文。

§1、§3.2、§8.1、§19.1 是**无条件否决**：没有任何证据形态可以触发重新评估。这类条文只有两种结局——被整体推翻，或永久遵守。前者代价过大，后者会让规格与实际演进方向长期背离，而每个具体 Change 只能选择静默违反或停滞。

§22 已有部分修订的先例：「第一阶段吸收平铺布局，先用安装清单形成逻辑边界，避免无价值的大规模路径搬迁」（`framework-unification.md:738`）——保留边界目标，改变实现承载。本 Change 沿用同一手法。

## 5. 目标

1. 在 §1、§3.2、§8.1、§19.1 四处拆开命题 A 与命题 B：语义差异保留为无条件约束，实现承载改为条件式。
2. 修正 §19.1 已被 §5.4、§6.3 推翻的 Artifact 理由，标注取代关系，不改写为「当初判断有误」。
3. 为 §3.2、§8.1 补充重新评估条件，格式与 §8.2 一致。
4. 给出「一条执行链」的**可判定定义**，使后续 Change 能被机器核验是否越界。
5. 保留 §19.1 第二条理由（条件分支膨胀）为硬约束，并将其转化为可核验的上限。
6. 更新 §21 中已被事实推翻的生产验证陈述，同时保留「已被使用」与「已被验证」的区分。

## 6. 非目标

- **不推翻任何语义差异**。§3.2 的五项差异、§5.3 与 §6.3 的强制规则一条不减。
- **不合并 Skill 入口**。§19.3（目录合并）与 §19.4（默认双装）不在本 Change 范围，其放弃理由未受影响。
- **不改任何脚本**。本 Change 只动 `openspec/specs/`，零代码改动。
- **不预先批准后续步骤**。补充条件不等于条件已满足；`governance_profile` 声明化、审批下沉、写状态路径迁移各自需要独立 Change 举证。
- **不改 §8.2 与 §8.3**。公共 AST 的提取由 change 2035 处理，本 Change 不重复裁决。
- **不处理 §21 的其他不确定项**。§21 共五条，本 Change 只动生产验证这一条；`arch-snapshots/` 时效性、发布平台边界、迁移工作量估算、基线要求四条不动。
- **不把「已被使用」升格为「已被验证」**。见 §8.3。

## 7. 「一条执行链」的可判定定义

条文若只写「允许收敛」，等于把边界交给下一个 Change 自由解释。本 Change 必须同时交出判据。三条候选判据，详见 `design.md` §3：

| 判据 | 内容 | 可核验性 |
| --- | --- | --- |
| 状态源唯一 | 任一时刻一个 Task 的状态只有一个写入者 | 静态可查 |
| 门为叠加 | Profile 门只增加转移的前置条件，不改变状态转移图本身 | 需转移图作为基线 |
| **降级等价** | 把 `governance_profile` 从 `production` 降到 `tooling`，剩余行为必须与纯 Tooling 逐字节相同 | **可机械核验** |

降级等价判据是 change 2035 的 golden 基线方法的推广，也是唯一能机械核验的一条。它同时防住 §19.1 第二条理由担心的条件分支膨胀：若分支已多到无法降级归一，判据自动失败。

## 8. 已裁决事项

以下三点已由用户于 2026-07-26 裁决，实现方按此执行，不再重开。

**8.1 §8.1 按读层、门层、写层三层拆分。** 未采用读／写两层的粗粒度方案：门层正是 Production 升级项的落点，其证据形态（审批记录、Review 档位、归档证据）与读写两层完全不同，并入写层会让解除条件失焦。三层各自独立标注状态与解除条件，见 `design.md` §2.3。

**8.2 §19.1 第一条理由保留原文，附「已被 §5.4、§6.3 取代」标注。** 未采用直接删除：`framework-unification.md` 是决策记录，删除理由会丢失当时的判断依据，无法让后来者判断条件是否真的变了。该处置与 §8.2 保留原判断依据的做法一致。

**8.3 §21 的生产验证陈述按事实更新，但不升格为「已验证」。**

§21 现文（`framework-unification.md:717`）：

```text
文档支持双 Profile 架构，但不能证明 Production OPSX 已经过真实生产项目验证。
```

该陈述已被事实推翻——框架作者声明已在真实生产项目中使用 Production Profile。但改写必须守住一条边界：**「已被使用」不等于「已被验证有效」**。前者由作者声明确立，后者需要遥测、缺陷记录或外部 Change 证据，仓库内目前一条都没有。

因此改写为「使用已确立、有效性证据仍缺失」的双段表述，而不是简单删掉这条不确定项。证据来源与日期须写入正文，使后来者能判断该结论的强度。具体措辞见 `design.md` §2.5。
