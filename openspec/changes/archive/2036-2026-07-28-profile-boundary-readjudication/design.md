# Design：双 Profile 收敛边界的条文改写

**变更**：profile-boundary-readjudication
**日期**：2026-07-26

---

## 1. 改写原则

三条，按优先级排列：

1. **语义强度不降。** 任何一处改写后，Production 现有的人工介入点、审批证据、Review 档位、归档要求、Verification 失败策略都不得变松。改写只动「谁来承载」，不动「要求什么」。
2. **条件可举证。** 新增的重新评估条件必须是能被一次 `grep`、一次测试或一份对照表证明的事实形态，与 §8.2 三条条件同级。不写「视复杂度而定」这类由读者自由裁量的措辞。
3. **保留原判断依据。** 被取代的理由标注取代关系，不删除、不改写为「当初有误」。`framework-unification.md` 是决策记录，抹掉推理过程会让后来者无法判断条件是否真的变了。

## 2. 逐处改写

以下为建议措辞。行号以当前 `framework-unification.md` 为准。

### 2.1 §1 决策结论（`:27`、`:31`）

**现文**

```text
- 把 Production 与 Tooling 强行合成一条工作流。
- 把两套 Tasks 控制逻辑合成一个巨型状态机。
```

**建议改写**

```text
- 在语义差异未被显式建模为可声明策略之前，把 Production 与 Tooling 合成一条工作流。
- 在缺少降级等价判据的前提下，把两套 Tasks 控制逻辑合成一个巨型状态机。
```

改写要点：两条都从「不采用某个终局形态」变为「不采用缺少前置条件的做法」。终局是否可取交给条件判定，而不是在决策结论里一次性关死。「巨型」二字保留——它本就指向失控规模，不指向合并本身。

### 2.2 §3.2（`:84-94`）

标题与五项差异列举（`:86-92`）**原样保留**，只改结论句。

**现文（`:94`）**

```text
因此必须保留两个独立生命周期，只共享场景无关的工程能力。
```

**建议改写**

```text
因此这五项差异必须始终存在，不得以「统一」为由删减任意一项。

差异的承载方式是独立问题。当前由两个独立生命周期承载；是否改由单一执行链加可声明治理策略承载，按以下条件重新评估：

1. 五项差异全部可表达为 Profile 可声明的策略参数，且每项都有机器可读的取值来源。
2. 存在降级等价判据的可执行实现：把 governance_profile 从 production 降到 tooling 后，剩余行为与纯 Tooling 逐字节相同。
3. Production 现有的强制规则（§5.3）在收敛后逐条仍可被机器门禁强制，不退化为散文要求。
```

改写要点：把一句话拆成「不可动的部分」与「可评估的部分」。条件 3 是最关键的一条——它防住「收敛过程中某个 OPSX 检查悄悄变成 `SKILL.md` 里的一句提示」。

### 2.3 §8.1（`:297-299`）

按 `proposal.md` §8.1 已裁决的三层拆分执行。

**现文**

```text
### 8.1 不建设巨型统一引擎

Production 校验器是只读生命周期裁决器；Tooling 控制器是有状态执行引擎。二者不能合并为同一个状态机。
```

**建议改写**

```text
### 8.1 不建设巨型统一引擎

Production 校验器是只读生命周期裁决器；Tooling 控制器是有状态执行引擎。二者的合并按三层分别评估，不作整体裁决。

| 层 | 内容 | 当前状态 | 解除条件 |
| --- | --- | --- | --- |
| 读层 | tasks.md 解析、任务边界、字段定位 | 条件已满足，见 §8.2 | 已解除 |
| 门层 | 审批、风险分级、Review 档位、交付与归档证据 | 未评估 | §3.2 三条条件全部满足 |
| 写层 | 任务状态写回、DAG waves、attempts、写锁、恢复 | 条件未满足 | 读层与门层均已合并且稳定运行；且写层合并后 Production 的只读性质有等价替代 |

「巨型」的可核验上限：任一层合并后，若降级等价判据无法执行或无法通过，即判定为越界，必须回退到合并前形态。
```

改写要点：写层的解除条件里「Production 的只读性质有等价替代」是硬点。`validate_change.py` 只读是 Production 可审计性的基础——校验器不改状态，所以它的判定永远可复现。写层合并会打破这条，必须先有替代方案，不能靠「加个只读模式开关」糊过去。

### 2.4 §19.1（`:653-658`）

**现文**

```text
### 19.1 强行收敛为一条工作流

放弃原因：

- Production 和 Tooling 的 Artifact、人工介入和执行策略不同。
- 单一路由会持续积累条件分支，最终形成难以理解的巨型 Skill。
```

**建议改写**

```text
### 19.1 无前置条件地收敛为一条工作流

放弃原因：

- Production 和 Tooling 的人工介入和执行策略不同。
  - 原文含「Artifact 不同」。该条已被 §5.4 与 §6.3 取代：两个 Profile 共用同一 Artifact 根目录与同一套 openspec 契约，差异已收敛到审批、Review、DAG、Worktree、失败恢复和 Runtime 审计六项。保留原文以记录当时判断依据。
- 单一路由会持续积累条件分支，最终形成难以理解的巨型 Skill。该风险的可核验上限见 §8.1 的降级等价判据。

本条放弃的是「无前置条件的收敛」。带条件的收敛路径见 §3.2 与 §8.1。
```

改写要点：标题加「无前置条件地」是全节的语义锚点——不改标题，正文再怎么写都会被当成整体否决继续引用。第一条理由按 `proposal.md` §8.2 已裁决的方式保留原文并附取代标注。

### 2.5 §21 生产验证陈述（`:717`）

**现文**

```text
- 文档支持双 Profile 架构，但不能证明 Production OPSX 已经过真实生产项目验证。
```

**建议改写**

```text
- Production OPSX 已在真实生产项目中使用（框架作者声明，2026-07-26）。但「已被使用」不等于「已被验证有效」：仓库内没有该使用的可核验材料——无遥测记录、无外部项目的 Change 归档、无缺陷或回归数据。因此 OPSX 各项门禁在真实生产压力下的有效性仍属未决，本条不作为「已验证」引用。
```

改写要点三条：

1. **保留未决项。** 这条原本就在「不确定性与实施边界」章节里，它的作用是提醒后来者不要把 Production 的治理强度当成已被实践检验的事实。直接删掉等于删掉这个提醒。
2. **写明证据来源与日期。** 「框架作者声明」是这条结论的全部依据强度，不写来源就会被当成有材料支撑的结论。日期让后来者能判断声明是否已过时。
3. **列出缺失的证据形态。** 遥测、外部归档、缺陷数据——写清楚缺什么，这条才有可能被后续证据关闭；只写「证据不足」则永远无法判定是否已补齐。

本条与 §2.1 至 §2.4 无依赖关系，可独立改写。它与本 Change 主线的共同点仅在于同属「规格陈述已被事实更新」这一类，不属于收敛边界裁决。

## 3. 「一条执行链」的可判定定义

写入位置建议为 §8.1 之后新增 §8.4，或并入 §8.1 表格下方。

### 3.1 三条判据

**判据一：状态源唯一。** 任一时刻，一个 Task 的状态字段只有一个写入者。`framework-unification.md` §3.3 已规定「校验器只读，不维护平行状态」「`workflow_control.py` 负责校验和原子写回，不另建平行状态」——判据一是这两条在收敛后的延续，不是新要求。核验方式：静态查找对 `- 状态:` 与任务头标记的写入点。

**判据二：门为叠加。** Profile 门只增加状态转移的前置条件，不新增、不删除、不重定向状态转移本身。即 `production` 能让一个转移**不发生**，但不能让它转向 `tooling` 下不存在的目标状态。核验方式：需要先把 Tooling 的转移图固化为基线，成本较高。

**判据三：降级等价。** 把 `governance_profile` 从 `production` 降到 `tooling` 后，对同一输入的执行结果必须与纯 Tooling 实现逐字节相同。

### 3.2 为什么以判据三为主

判据一是必要条件但不充分——两套逻辑各自只读一半状态也能满足。判据二最贴近「叠加而非替换」的直觉，但要求先有转移图基线，而该基线目前不存在。

判据三可机械核验，且方法已在 change 2035 验证过：golden 基线 + 逐字节比对。它还顺带覆盖了 §19.1 第二条理由——分支膨胀到无法降级归一时，判据自动失败，不需要另设「Skill 复杂度上限」这类无法量化的指标。

**失败后果**：判据三无法执行（例如降级路径不存在）与判据三执行后不通过，同等处理，均判定为越界，必须回退到合并前形态。「无法执行」不得按「暂不适用」放行——这正是 §19.1 担心的失控形态。

### 3.3 判据三的已知局限

降级等价只能证明「production 关掉后等于 tooling」，不能证明「production 打开后治理强度不低于现在的 Production」。后者需要独立的强度对照，属于 §3.2 条件 3 的范围，不由判据三承担。两者必须同时满足，缺一不可。

## 4. 关键权衡

**为什么不直接把三处禁令删掉。** 删掉最省事，但会同时删掉命题 A——语义差异必须保留这条约束就没有文本依据了。收敛过程中最大的风险不是技术难度，而是「统一」被当成删减的理由。禁令改写后仍然是禁令，只是禁的对象从「终局形态」变成「无条件的做法」。

**为什么条件写得比 §8.2 更严。** §8.2 的三条条件是「提取一个只读解析模块」的门槛，代价可控、可回退。§3.2 与 §8.1 门层／写层的条件对应的是治理结构变更，一旦落地，回退需要重建两套实现。条件严一档是刻意的。

**接受条文变长。** 改写后 §8.1 从两句变成一张表加一条判据说明。可读性下降，换取的是后续每个 Change 都能自查是否越界，而不是各自解释「这算不算合并」。当前的两句话简洁但不可判定，这是它需要改的根本原因。

## 5. 已知限制

- **本 Change 不验证任何条件是否已满足。** §3.2 三条、§8.1 门层与写层的条件在本 Change 交付后全部处于「未举证」状态。读层是唯一例外，由 change 2035 举证。
- **判据三尚无实现。** `governance_profile` 目前不存在，降级路径也不存在。判据是为后续 Change 立的标尺，本 Change 不建设它。
- **反向引用范围未知。** 引用这四处结论的文档由 Task 1 清点，改写前无法预估波及面。若清点结果显示波及 Skill 散文，需评估是否拆分 Change。
- **§21 改写不提高证据强度。** 见 §2.5。改写后「Production 已在生产项目使用」的唯一依据仍是作者声明，仓库内无可核验材料。该条目仍属未决项，只是未决的内容从「是否使用过」变为「使用效果是否被验证」。
