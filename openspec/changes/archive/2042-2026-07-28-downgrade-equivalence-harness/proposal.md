# Proposal：降级等价判据的可执行实现

**作者**：YanQiu0207（AI 辅助）
**日期**：2026-07-26
**变更**：downgrade-equivalence-harness
**状态**：Draft

---

## 1. 问题

change 2036 把「降级等价」定为收敛的主判据，但它目前只是条文，没有可执行的实现。

判据内容（`framework-unification.md` §8.1，由 change 2036 引入）：

> 把 `governance_profile` 从 `production` 降到 `tooling` 后，对同一输入的执行结果必须与纯 Tooling 实现逐字节相同。

以及失败后果：

> 判据无法执行与判据不通过同等处理，均判定为越界，必须回退到合并前形态。「无法执行」不得按「暂不适用」放行。

要执行这个判据，需要两样目前都不存在的东西：

1. **可切换的降级路径**——能把 `governance_profile` 从 `production` 降为 `tooling` 的开关。
2. **比对基线**——「纯 Tooling 实现」的输出，用来和被降级后的 Production 输出逐字节比对。

没有这两者，判据是空话；有了这两者，每一次门层改动都能被机械核验是否越界。

## 2. 前置依赖

本 Change 不独立成立，依赖：

| 依赖 | 提供什么 | Change |
| --- | --- | --- |
| 治理 Profile 可声明 | 可切换的 Profile 开关与 `--governance-profile` 参数 | change 2041 |
| 收敛边界条文 | 判据的定义、失败后果与越界处理 | change 2036（已交付） |

change 2041 交付前，本 Change 没有可降级的开关，无法执行。

## 3. 判据能验什么，不能验什么

change 2036 的 `design.md` §3.3 已写明判据的局限，这里复述因为它决定本 Change 的范围：

| 判据能验 | 判据不能验 |
| --- | --- |
| 关掉 `production` 后等于纯 `tooling` | 打开 `production` 后治理强度不低于现状 |

也就是说，降级等价只能证明「Production 是 Tooling 的严格超集，减去治理门后就是 Tooling」。它**不能**证明 Production 的治理门本身正确、完整或够强。

后者由 §3.2 条件 3 承担（Production 强制规则逐条仍可机器强制），不在本 Change 范围。**本 Change 只建设降级方向，不触碰治理强度证明。** 两者必须同时满足，缺一不构成收敛。

## 4. 目标

1. 提供可执行的降级路径：同一输入分别按 `production` 与降级到 `tooling` 的方式处理。
2. 生成纯 Tooling 的比对基线。
3. 逐字节比对两种输出，给出通过／不通过／无法执行三种明确结论。
4. 「无法执行」与「不通过」同判为越界，不静默放行。
5. 实现可被后续门层 Change 复用，作为每次改动的回归门。

## 5. 非目标

- **不证明治理强度**。见 §3。
- **不合并任何门层逻辑**。本 Change 只建判据的执行框架，不改动任一轨的门。
- **不替 change 2041 补开关**。若 2041 未交付，本 Change 停止，不自建 Profile 读取。
- **不改写既有门禁脚本的行为**。只新增独立的比对器，四轨门禁的判定内容不动。
- **不覆盖全部 Production 强制规则**。判据只验「减去治理门后等于 Tooling」，不逐条验 §5.3。

## 6. 设计方案

### 6.1 比对器的输入与输出

降级等价比对是一个独立脚本，不寄生在任一轨门禁里：

```
输入：同一组 tasks.md（或 Change 目录）
  路径 A：按 production Profile 处理，但 governance_profile 降为 tooling
  路径 B：按纯 tooling Profile 处理
输出：通过 / 不通过 / 无法执行
```

**「路径 A 的降级」是本 Change 唯一新增的机制。** 它不是修改 Production 门禁，而是在 Production 处理链上注入一个「忽略治理门」的降级开关。开关由 change 2041 的 `--governance-profile` 提供。

### 6.2 逐字节比对的范围

「执行结果」需要定义边界，否则比对无从下手。候选范围，按可比性从高到低：

| 候选输出 | 可逐字节比吗 | 说明 |
| --- | --- | --- |
| 门禁退出码 | 可 | 太粗，只反映成败 |
| 错误码集合 | 可 | 中等粒度 |
| 结构化判定输出（错误编号 + 路径 + 消息） | 可 | **倾向采纳** |
| 完整 stdout 含时间戳 | 不可 | 含非确定性内容 |

倾向比对「结构化判定输出」——退出码加排序后的错误编号集合。含时间戳或绝对路径的输出需先做确定性归一，归一规则必须显式写出，不得静默丢弃差异。

### 6.3 「无法执行」的判定

判据无法执行的情形必须枚举，否则会被默认放过：

| 情形 | 判定 |
| --- | --- |
| `--governance-profile` 开关不存在 | 无法执行 |
| 降级路径未实现（开关存在但无效果） | 无法执行 |
| 比对基线不存在 | 无法执行 |
| 两路径输出格式不可比 | 无法执行 |
| 降级后输出与纯 Tooling 不一致 | **不通过**（不是无法执行） |

最后一行是关键区分：跑出了结果但不一致，是「不通过」；跑不出结果，才是「无法执行」。两者都判越界，但原因不同，报告里必须分开。

### 6.4 未裁决项

**降级开关的实现位置。** 是在各门禁脚本里加「降级模式」，还是用一个独立包装脚本在调用层剥离治理参数。前者改动分散到四个脚本，后者集中但可能在某些路径剥不干净。倾向后者，并由本 Change 的「无法执行」判定兜底剥不干净的情况。

**比对基线的生成时机。** 纯 Tooling 基线是预先冻结（golden），还是每次现跑现比。预冻结更稳但会过期，现跑更新快但两路径若同步漂移会同时错。倾向现跑现比加定期 golden 复核，具体由实现方定。

## 7. 验收标准

1. 提供可执行命令，对同一输入分别走「production 降级到 tooling」与「纯 tooling」两条路径。
2. 两条路径的结构化判定输出可逐字节比对。
3. 给出通过／不通过／无法执行三种结论，退出码与报告区分三者。
4. 「无法执行」的五种情形逐一枚举并各有用例。
5. 「不通过」与「无法执行」同判为越界，但报告分开标注原因。
6. 「无法执行」不得按「暂不适用」放行，有用例证明默认即失败。
7. 比对范围（退出码 + 错误编号集合，含确定性归一规则）显式写出，归一不静默丢弃差异。
8. 降级开关的实现位置已裁决并记录理由；若选包装脚本，「无法执行」判定覆盖剥离不全的情形。
9. 比对基线生成时机已裁决并记录理由。
10. 本 Change 不改动任一轨门禁的既有判定内容；四个门禁脚本对全部活跃与归档 Change 的输出与改动前一致。
11. 判据的局限（不证明治理强度）写入输出报告头部，不被读成「收敛已证明」。
12. `python -m pytest scripts -q` 全量通过。
13. 按 md-zh 规范自检中文排版。
