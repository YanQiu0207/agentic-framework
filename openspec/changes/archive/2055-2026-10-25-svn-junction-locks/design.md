# 设计：逻辑项目根与真实任务身份分离

**状态**：Approved

## 4. 根定位

`_repository_root(path)` 先通过 `_task_project_directory()` 取得逻辑检查起点，跳出固定 `openspec` 知识入口内部的链接，再从该目录及祖先检测 `.git` 或 `.svn/wc.db`。这样知识目标本身是独立 Git／SVN 仓库时，也不会把目标标记误当所属项目根。未命中才从 `path.resolve(strict=False)` 的祖先查询，仍未命中返回真实任务目录。根定位只选作用域，不替代 VCS 后端探测；Git／SVN 并存的后端选择规则不变。

## 5. CLI 作用域

用户追加批准的 `route`／`recover`／`init-run` 检查通过 `_task_project_directory()` 取得检查起点，再调用现有 VCS／能力接口。普通路径保持任务父目录，保留嵌套项目的 manifest 与双 VCS 边界；仅在任务父目录到最近 `openspec` 入口（含入口）之间逐组件比较真实路径，扫描完整范围后使用最外侧知识链接的逻辑父目录，防止多层链接仍停留在外置知识仓库内部。项目根本身是 Junction 时不越出项目，因为整个项目别名不属于知识入口内部链接。不能简单对所有命令传仓库根，否则可能越过嵌套项目的独立 manifest。

不修改公共 VCS 实现，不允许绕过 SVN Runtime 拒绝或双 VCS 显式选择规则。测试核对实际检查目录，并覆盖普通与 Junction 嵌套项目边界。

## 6. 写锁实现

`_task_lock_path(path)` 保持真实路径规范化摘要作为锁名，但通过原始路径取得项目根。新增 `_task_identity_lock_path(path)`，以相同摘要在系统临时目录的 `agentic-framework/workflow-locks/` 放置共享锁。

`_task_write_lock()` 按「已存在的旧相邻锁 → 真实身份锁 → 项目锁」的固定次序取得锁，使用同一个 deadline，由 `ExitStack` 反向释放。身份锁解决不同逻辑项目根下项目锁不相同的问题；保留项目锁避免破坏同根既有进程的互斥。锁文件不主动删除，避免删除后重新创建造成锁身份分裂。

## 7. 验证与限制

测试复用现有临时目录、子进程竞争及任务正文断言；Windows Junction 使用 `cmd /c mklink /J` 创建，原生命令以字节捕获再安全解码，不假定 UTF-8。Python 子进程同时设置 `PYTHONUTF8=1` 与 `PYTHONIOENCODING=utf-8` 并显式解码。增加 CP936 环境覆盖。

本次不建立通用锁框架，不改变公开接口、状态转移或原子写入协议。依赖相同系统临时目录，网络共享及跨用户写入不在保证范围内。根识别沿用轻量标记探测，不执行 SVN 命令。

新版保留项目锁以兼容同根既有进程，但旧版在 Junction 目标目录生成的锁与新版逻辑项目锁位置不同，不保证新旧版本混跑互斥；共享任务的写入进程应一起升级。

## 8. 验证顺序

用户明确要求开发阶段只跑定向测试，不反复正式 Verify。执行期先完成定向回归与真实 SVN CLI 用例，冻结代码、规格正文和归档目录后集中运行一次配置驱动全量验证。最终验证后仅通过状态机补齐任务执行字段和依据实际结果勾选复选框；这些执行元数据由现有 Native 内容主体算法规范化，不改变已冻结需求正文。

首轮将审查与全量验证并行，审查发现两个边界问题后已中止旧快照验证，保留原报告。修复后先完成定向复审，再重新冻结最终快照并集中验证，不重复首审或重采基线。

## 9. 取舍与回滚

架构决策：将逻辑项目作用域与真实任务身份分开；放弃只用项目锁的方案，因为不同逻辑根可共享同一真实任务。保留公共 VCS／能力接口和旧锁兼容，不增加配置项或公开 API。若需回滚，必须先停止共享任务的写入进程，避免新旧锁位置混跑；当前任务不自动回滚任何真实业务项目。
