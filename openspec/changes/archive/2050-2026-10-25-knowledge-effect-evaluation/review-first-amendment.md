## 目标与边界

通用实验管理与场景评分分离，首个场景为代码 Review。原先代码生成、Docker 隐藏测试验收延后，不在本轮实现。用户已认可后续团队知识对 Review 的影响主要复用实验配置；代码生成效果实验还需新增隔离执行与测试验收。

## 首版合同

- 使用 JSON 定义 Task、Treatment、Experiment 及任务 × 分组 × 重复次数矩阵，冻结公开代码、私有预期问题、知识材料及执行条件。
- 导出仅含任务要求、待审代码、所选知识的白名单输入，不导出预期问题、评分规则或私有主机路径。
- 导入结构化 Review findings、来源声明与可选用量，不启动模型或执行任何提交代码；快照不可覆盖，拒绝路径穿越、链接和重复身份。
- 人工裁定文件绑定计划、单元及提交摘要，将每个 finding 映射至一个预期问题或误报。重复发现不能重复增加检出数；未裁定保留 pending，不推测语义匹配。
- 分开报告检出、漏报、误报、严重度准确度、执行失败、缺失记录和未裁定记录。零分母使用 null，不把缺失费用记零。
- 按相同任务和重复编号配对，展示预定矩阵全部单元；业务规则、架构踩坑、编码规范作为知识分类，支持 CONTROL／KNOWLEDGE 对比。
- 来源及裁定者身份是声明，不代表机器验证了隔离或独立性。合成案例只验证评测合同，不证明真实模型或知识收益。

继续使用原 Verify 基线与基准提交；旧 Run 保留，不冒充新范围证据，新 Run 绑定本修订。最终仍采用独立严格审核，不因范围调整降低已选验收要求。

## 真实历史案例试点

用户要求以成熟大仓库历史 Bug 测试 Review 技能效果，而非以合成案例推断能力。选用固定版本的 Astropy、Django、pytest 和 scikit-learn 历史修复，隐藏修复补丁与预期问题，比较直接审查与实际派发综合审查员的技能组。

本轮使用独立 AI 对结果做初评，不冒充人工复核。评测器只导入外部裁定，不调用 Judge，也无法验证提供者是否为人；报告中的证据措辞须改为「外部提供的裁定，身份未验证」，不能硬编码已由人类裁定。清单外有效问题保持待定，不强制当作误报。标准阶段的发现与完整治理流程完成率分开说明，未执行的 strict 升档不能称为完成。
