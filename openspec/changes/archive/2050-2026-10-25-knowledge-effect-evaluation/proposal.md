# 团队知识效果评测框架

**日期**：2026-10-25
**状态**：Archived

> 本文保留最初知识效果方向；实际交付范围以 review-first-amendment.md 为准，包含 Review 框架与真实历史案例试点。

## 1. 问题与目标

用户批准借鉴 Comet 的评测方法，而非集成 Comet；随后明确优先验证「有／无团队知识对代码效果的影响」。现有 `scripts/evaluation_runner.py` 偏行为合同检查，`scripts/benchmark_runner.py` 汇总历史真实任务；本次不修改两者口径或运行时探测协议。

### 首版范围

- 用 JSON 定义任务、知识实验组和重复次数；CONTROL 与 KNOWLEDGE 使用同一任务、初始代码和隐藏验收，仅知识内容不同。
- 冻结任务、验收、知识、执行条件与实验矩阵；导出公开输入时不得包含隐藏测试、期望答案、评分规则或其宿主路径。
- 支持导入已有 Agent 代码产物和来源声明，保留不可覆盖的逐次记录；导入证据不能宣传为框架已验证的隔离执行。
- 隐藏验收仅在显式授权的 Docker 容器中运行生成代码，不在宿主执行不可信代码；测试和 Agent 不同时运行，不向被测 Agent 导出测试。
- 分开报告通用正确性与团队约束、失败／错误／未执行、成本缺失和来源可信度；按任务与重复编号配对，报告预定矩阵中的所有缺失尝试。
- 提供合成代码任务，包含知识有助于完成的团队规则、通用正确性检查，以及知识无关的对照检查。合成案例只验证工具链，不能证明真实团队收益。
- 以离线测试和模拟容器进程验证主链路；本次不下载镜像、不调用模型、不运行真实容器。

### 非目标与后续阶段

本轮不接入 Comet、模型 SDK、云遥测或自动 Judge；不将 LLM 评分当作测试通过。自动宿主执行器在确认宿主与预算后接入公开输入协议；首版导入模式不能证明无全局知识污染，也不能把来源声明包装成机器探测。原先 Review 专项案例被本次团队知识效果任务替代。

### 验收标准

1. 相同输入产生可复现计划；不合法路径、重复 ID、非法重复次数、缺失输入均拒绝。
2. CONTROL 不接收团队知识；KNOWLEDGE 接收明确快照；两组任务与验收一致。
3. 公开输入不含隐藏验收与期望答案；输入内容变更导致旧证据不可冒充当前计划。
4. 导入快照与记录不可覆盖，拒绝链接、路径穿越与特殊文件；没有本次授权不得启动容器或模型。
5. 测试未执行、进程错误、无测试、非法报告、超时和中断均不能记为通过；容器无网络且不挂载工作仓库、用户主目录或 Docker socket。
6. 配对报告包含缺失记录、不确定来源和不可得指标，不用零代替缺失费用；不复制 Comet 的 `pass^k` 口径。
7. 离线单元／集成测试覆盖上述路径；Windows 子进程 UTF-8 行为须测试。

## 2. 设计方案

新增 `scripts/knowledge_eval.py` 作为薄 CLI／实验层；仅在需要独立可测边界时拆出辅助模块。示例位于 `evaluation/knowledge-effect/`，测试位于 `scripts/test_knowledge_eval.py`。实现遵循现有 Python 标准库风格。

流程：定义 → 冻结计划与公开输入 → 人工或后续可信执行器生成代码 → 导入快照与来源声明 → 显式容器验收 → 配对报告。执行条件属于声明，只有实际采集的数据才能称为观测值。人工导入数据的报告须醒目标明该限制。

Docker 验收仅消费复制好的提交与固定隐藏测试，容器生命周期有超时与取消处理，输出有限制。Docker daemon 和预装镜像属于可信计算边界；首版不承诺防御恶意宿主或所有容器逃逸。敏感团队知识与代码均只保留本地，不自动发送到任何服务。
